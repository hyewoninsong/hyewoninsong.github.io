SuperPDF 의 마인드맵은 밑줄을 그을 때마다 노드가 하나 생긴다. 지금까지 그 노드는 같은 부모 아래 마지막 밑줄 노드 뒤에 붙었다. 앞에서 뒤로만 읽으면 그게 곧 책 순서라 문제가 없었는데, 20쪽을 읽다가 10쪽으로 돌아가 한 줄 더 긋는 순간 그 노드는 20쪽 뒤에 붙었다. 나중에 밑줄만 다시 읽는 사람에게 맵이 책과 다른 순서로 놓인다는 건 맵을 안 보게 된다는 뜻이다. 오늘 이 규칙을 바꾸고, 맵을 만지는 방법도 손봤다.

## 새 노드는 책 순서 자리에 끼어든다

PDF 를 가리키는 노드(밑줄, 손글씨, 잘라 낸 영역, 목록에서 "맵에 추가")는 이제 형제 사이에서 자기 자리를 찾는다. 기준은 파일 순서, 페이지, 페이지 안에서 위쪽부터. 규칙은 셋뿐이다.

| 형제 목록에 | 새 노드가 가는 곳 |
|---|---|
| 나보다 앞이거나 같은 자리의 밑줄 노드가 있다 | 그중 마지막 것 바로 뒤 |
| 전부 나보다 뒤다 | 첫 밑줄 노드 앞 |
| 밑줄 노드가 하나도 없다 | 맨 끝 (지금까지와 같다) |

어느 부모 아래로 가는지는 바뀌지 않았다. 노드를 선택해 두면 그 옆(밑줄 노드면 형제, 챕터나 메모면 자식), 아무것도 선택하지 않았으면 그 페이지의 챕터 아래다. 바뀐 건 형제 사이의 위치 하나다.

## 맵을 손과 키보드로

| 조작 | 동작 |
|---|---|
| 탭 | 선택하고, 밑줄 노드면 PDF 의 그 자리로 점프 (그대로) |
| 선택한 노드 오른쪽 + 버튼 | 자식 추가. 바로 인라인 편집이 열린다 |
| 노드를 끌어 화면 가장자리에 대면 | 캔버스가 그쪽으로 계속 스크롤 |
| Tab / Return | 자식 추가 / 뒤에 형제 추가 |
| 화살표 | 형제·부모·첫 자식으로 선택 이동. 접힌 노드는 → 로 펼친다 |
| ⌘↑ ⌘↓ | 형제 사이 순서 바꾸기 |
| Space / Esc / ⌫ | PDF 로 점프 / 취소 / 삭제 |

새 노드는 어떤 경로로 만들든 빈 칸으로 열리고, 비운 채 나가면 사라진다. 루트를 만들 때 뜨던 "노드 추가" 알림창은 없앴다. 그 알림창 하나만 다른 입력 방식이었다.

밑줄로 자동 생긴 노드는 맵이 그 자리로 스크롤해 한 번 깜빡인다. 단 부모가 접혀 있으면 펼치지 않는다. 접어 둔 건 접어 둔 이유가 있고, 접힌 노드의 숨은 개수 배지가 하나 올라가는 걸로 충분하다.

## 국소 삽입을 고른 이유

전체를 책 순서로 다시 정렬하는 쪽이 코드는 짧다. 버린 이유는 손으로 옮긴 순서가 다음 밑줄에서 되돌아가기 때문이다. 이 맵은 자동으로 채워지는 목록이 아니라 읽으면서 정리하는 곳이라, 사용자가 옮긴 자리는 사용자 것이어야 한다. 국소 삽입은 그 사이에 끼어들기만 해서 손 배치가 대부분 살아남는다.

부모마다 "수동 정렬" 플래그를 두고, 한 번이라도 손을 댔으면 끝에 붙이는 안도 있었다. 상태가 하나 늘고, 그 플래그가 켜졌다는 사실을 사용자가 알 길이 없어서 버렸다. 색으로 묶는 건 처음부터 아니었다. 색은 의미로 고르는 것이지 위치가 아니다.

탭하면 PDF 로 점프하는 규칙은 "부모를 고르려고 탭했는데 PDF 가 움직인다" 는 걱정 때문에 바꿀까 했다가 그대로 뒀다. 부모가 될 노드는 챕터나 메모라 PDF 참조가 없고, 참조가 없는 노드는 점프하지 않는다. 충돌하는 경우가 실제로는 없었다.

## count 는 다음 번호가 아니었다

작업 중에 예전 버그 하나가 드러났다. 자식을 붙일 때 순번을 `children.count` 로 매기고 있었다. 자식이 셋일 때 가운데를 지우고 하나 더 붙이면 새 노드가 2번을 받는데, 살아남은 셋째도 2번이다. 같은 번호 둘은 정렬할 때마다 앞뒤가 바뀔 수 있어서, 레이아웃을 다시 그릴 때 두 노드가 자리를 바꾸는 것처럼 보인다. 데이터 버그인데 증상은 깜빡임이라 오래 남아 있었다.

최상위 노드는 처음부터 `max + 1` 로 매기고 있었다. 같은 값을 두 곳이 다르게 계산한 게 원인이라, 자식도 `max + 1` 로 바꾸고 형제 사이에 끼울 때는 0부터 다시 매긴다. 이미 저장된 중복도 그때 같이 고쳐진다. 테스트는 "셋 만들고, 가운데 지우고, 하나 붙이면 번호가 전부 다르다" 하나다. 만들기만 하는 픽스처로는 절대 안 걸린다.

하나 더. 밑줄을 되돌리기로 지우면 노드도 사라지는데, 뷰모델의 `selectedNodeId` 는 사라진 노드의 id 를 계속 들고 있었다. 맵 안에서 지우는 경로는 선택을 비우고 있었지만, 되돌리기는 장부가 뷰모델을 거치지 않고 노드를 없앤다. 드래그 중인 노드 id 는 이미 정리하고 있었고 선택만 빠져 있었다. 하나만 정리하고 있으면 나머지도 같은 결함이라고 보는 게 맞았다. 이제 노드 색인을 다시 만드는 자리에서 선택·편집·드래그 id 를 전부 대조한다.

## 남은 것

iPad Pro 11인치 시뮬레이터에서 유닛 테스트 964개가 돈다. 키보드는 아직 손으로 안 눌러 봤다. 검색 칸에 커서가 있을 때의 ⌫ 와, PDF 쪽을 보고 있을 때의 Space 가 맵을 먼저 잡는지 확인해야 한다. Tab 으로 만든 빈 노드를 Esc 로 버렸을 때 펼쳐진 부모를 다시 접을지는 아직 정하지 않았다.

## 2026-09-24 — 자식을 오른쪽이 아니라 아랫줄에, 노드는 그냥 끌면 움직인다

같은 날 저녁, 아이패드로 실제 책을 읽은 뒤 보고가 넷 왔다. 펜으로 만든 노드가 잘 안 끌린다, 자식이 오른쪽에 붙어 가로 스크롤을 해야 한다, 한글 띄어쓰기가 여전히 깨진다, 그래프와 표도 노드로 넣고 싶다. 넷 중 셋은 맵을 만지는 방법의 문제였다.

### 개요 모양으로

![자식이 부모 아랫줄에 들여쓰기로 붙고, 형제들이 세로 줄기 하나를 나눠 쓴다](/blog/superpdf-mindmap-placement/outline-map.png)

자식은 이제 부모 오른쪽이 아니라 **부모 아랫줄에 28pt 들여쓴 자리**에 순서대로 쌓인다. 연결선은 부모 바닥에서 수직으로 내려와 각 자식의 왼쪽 가운데로 꺾이는 ㄴ 자다. 형제들이 같은 줄기를 나눠 쓰니 파일 트리처럼 어디까지가 한 부모의 자식인지 한눈에 보인다. 깊이가 늘어도 가로로는 들여쓰기만큼만 늘어서 가로 스크롤이 거의 없어졌다. 읽는 방향과 맵의 방향이 같아진 것이 더 큰 변화다. 밑줄은 위에서 아래로 그어지고, 맵도 위에서 아래로 읽힌다.

수평 트리를 두고 자동 접기를 붙이는 안은 펼치는 순간 다시 옆으로 뻗어서 버렸다. 가로/세로 토글은 배치 둘의 드롭 판정과 핸들과 스크롤을 전부 두 벌로 유지해야 해서 버렸다. 원한 건 ㄴ 자 하나였다.

맵이 화면보다 길면 처음 열 때 가운데가 아니라 **위에 맞춘다**. 개요를 가운데 맞추면 첫 노드가 판 위로 잘려 나갔다.

![PDF 위, 맵 아래로 나뉜 화면에서 맵이 첫 노드부터 보인다](/blog/superpdf-mindmap-placement/outline-split.png)

### 선택하지 않아도 끌린다

"펜으로 만든 노드가 안 끌린다" 는 사실 모든 노드의 문제였는데, 밑줄을 긋고 방금 생긴 노드를 바로 옮기려는 흐름에서만 눈에 띄었다. 노드의 드래그 제스처가 **선택된 노드만** 받고 있었다. 노드 뷰는 더블탭(편집)을 단일 탭(선택)보다 먼저 붙여 두었고, SwiftUI 는 그러면 단일 탭을 더블탭 실패 판정 뒤 0.3초쯤 지나서야 보낸다. 탭하고 바로 끌면 첫 `onChanged` 시점에 선택이 아직 없다. 조건에 걸려 노드 드래그는 시작되지 않고, 같은 터치를 함께 받는 캔버스 패닝만 남는다. 잠깐 기다렸다 끌면 되고, 바로 끌면 캔버스가 움직인다. 사용자 말대로 "잘 안 된다" 였다.

고치는 방법은 조건을 빼는 것이었다. 어느 노드든 바로 끌리고, 끌기 시작하면 그 노드가 선택된다. PDF 로 점프하지는 않는다. 길게 눌러 들어 올리는 안은 노드의 길게 누르기가 이미 컨텍스트 메뉴라 안 됐다. 단일 탭을 즉시 처리하는 안은 더블탭마다 PDF 점프가 먼저 일어나서 안 됐다.

왜 못 잡았나. 드래그 테스트는 전부 `startDragging` 을 직접 불렀다. 제스처의 시작 조건은 뷰 안에 있어 단위 테스트가 닿지 않고, 시뮬레이터에서는 "탭 → 잠깐 → 끌기" 로 확인했다. 탭 직후 끌기의 0.3초는 사람이 자연스럽게 하는 동작이지 스크립트가 하는 동작이 아니다. 규칙으로 남긴 건 하나다. 제스처의 시작 조건을 다른 제스처가 비동기로 만드는 값에 걸지 않는다.

같은 이유로 잘라 낸 영역 노드의 이미지도 바뀌었다. 이미지가 노드를 거의 다 덮는데 이미지 탭이 곧바로 전체 크기 미리보기를 열어서 그 노드를 선택할 자리가 없었다. 이제 첫 탭은 선택, 선택된 뒤 한 번 더 탭하면 미리보기다. 빈 공간에 놓았을 때는 손가락이 걸친 줄의 가장 가까운 노드 기준으로 앞·자식·뒤를 판정한다. 개요에서는 노드 오른쪽이 늘 빈 공간이라 "그 줄 옆" 이라는 뜻이 분명하다.

### 캔버스는 맵을 놓치지 않는다

패닝도 손봤다. 캔버스를 무한히 끌어 맵을 시야에서 잃어버릴 수 있었다. 이제 맨 위 노드 위로, 맨 왼쪽 노드 왼쪽으로는 못 간다. 오른쪽과 아래도 같다. 딱딱하게 막지는 않는다. `UIScrollView` 와 같은 식 `(1 - 1/(x·0.55/d + 1))·d` 로 넘을수록 덜 끌리고, 손을 떼면 스프링으로 경계에 돌아온다. 핀치가 끝났을 때, 화면이 돌아갔을 때, 노드로 스크롤할 때도 같은 경계 안이다.

### 잘라 낸 그래프와 표

영역을 잘라 이미지 노드로 넣는 도구는 이미 있었다. 툴바의 크롭 모드에서 영역을 끌면 그 부분이 그대로 노드가 된다. 다만 스택으로 쌓은 PR 이 main 에 닿지 못해 테스트 빌드에 들어간 적이 없었다. 이번에 그 줄기를 main 과 합쳐 같이 나간다. 이미지 칸은 160pt 폭에 이미지 비율대로 48~120pt 높이라, 납작한 표가 120pt 칸 가운데 떠서 위아래가 비는 일은 없다.

### 띄어쓰기는 어디서 깨졌나

한글 띄어쓰기는 실험부터 했다. 명조와 고딕으로 양쪽정렬한 문단을 흐리게 하고 JPEG 으로 뭉개고 저해상도로 낮추고 살짝 기울여 Vision 에 넣었다. 글자를 제대로 읽은 149줄에서 공백 위치는 전부 맞았다. 틀린 건 저해상도에서의 글자 오인식뿐이었다. 그러니 활자체 책에서 띄어쓰기가 깨지는 건 인식기가 아니라 우리 쪽이다. 페이지 전체를 미리 읽어 두는 경로가 글자 좌표로 띄어쓰기를 되살리는 단계를 건너뛰고 있었다. 이제 두 경로가 같은 단계를 지난다. 책 활자체로 만든 스캔 흉내 이미지가 앱의 렌더 경로를 통째로 통과하는 테스트가 그 자리를 지킨다. 실제 스캔본에서 또 깨지면 그 페이지 한 장이 다음 재료다.

### 남은 것

유닛 테스트 994개가 돈다. 실기에서 볼 것은 셋이다. 밑줄을 긋고 바로 노드를 끌기, 가장자리 너머로 당겨 저항을 느끼기, 스캔한 책에서 표를 잘라 넣기.
