하루 플래너에는 계정이 없다. 가입도 로그인도 없고 데이터는 전부 기기 안에 있었다. 그런데 아이폰에서 짠 하루를 아이패드에서도 보고 싶다는 건 너무 당연한 요구고, 그걸 들어주자고 회원가입 화면을 만들 수는 없었다. 이제 두 기기가 같은 플랜을 본다 — 앱에 추가된 로그인 화면은 없다.

## 계정을 만들지 않는 쪽으로

로그인 없이 "같은 사람의 여러 기기"를 묶는 길은 사실상 하나뿐이다. **CloudKit private database**. 기기에 이미 로그인돼 있는 Apple 계정을 그대로 쓰고, 앱은 계정에 대해 아무것도 알 필요가 없다. SwiftData 는 저장소 설정 한 줄로 이걸 켠다.

다른 길들이 왜 밀렸는지가 결정의 절반이다.

- **자체 백엔드 + 계정 로그인** — 화면 하나가 아니라 제품이 하나 더 는다. 가입, 로그인, 비밀번호 찾기, 탈퇴, 서버, 비용. 안드로이드나 웹으로 갈 계획이 없는 지금은 이 전부를 "아이패드에서도 보이게" 하나에 쓰는 셈이다.
- **JSON 내보내기·가져오기** — 구현은 제일 싸다. 그런데 수동이고 실시간이 아니다. 아침에 아이폰에서 고친 걸 점심에 아이패드에서 보려고 파일을 주고받을 사람은 없다.
- **iCloud 키-값 저장소만 쓰기** — 1MB 한도에 관계가 있는 레코드를 밀어 넣을 수는 없다. 설정값에는 실제로 이걸 썼다.
- **Handoff** — "하던 화면 이어받기"이지 저장 동기화가 아니다. 애초에 다른 문제를 푼다.

## 대가는 스키마 제약 셋

CloudKit 으로 미러링하는 순간 모델이 CloudKit 레코드로 옮겨질 수 있어야 한다. 제약은 셋이다.

| 제약 | 이유 |
|---|---|
| `@Attribute(.unique)` 금지 | CloudKit 에 unique constraint 라는 개념이 없다 |
| 비옵셔널 속성엔 기본값 | 다른 기기가 만든 레코드에 이 기기가 모르는 필드가 비어 올 수 있다 |
| **모든** 관계는 옵셔널 + inverse | 관계의 양쪽이 따로 도착할 수 있다 |

(이 표의 셋째 줄은 처음 쓸 때 "to-one 관계는" 이라고 적혀 있었다. 그게 틀렸다는 걸 이틀 뒤에 알았다 — 맨 아래.)

세 모델의 `id` 에 붙어 있던 `@Attribute(.unique)` 를 다 떼고, `title` · `startMinute` 같은 비옵셔널 속성에 기본값을 달았다. 유일성은 어차피 UUID 가 보장하고 있었으니 실제로 잃은 것은 없다. 스키마 버전만 v3 으로 올라갔고 경량 마이그레이션으로 그대로 열린다.

## 위반은 크래시가 아니라 침묵이다

여기가 이 작업에서 제일 놀란 부분이다.

제약을 어기면 저장소 컨테이너 생성이 **던진다**. 그런데 던진 걸 받아서 CloudKit 없이 다시 열면 앱은 아무 일 없었다는 듯 뜬다. 화면도 정상, 데이터도 정상, 동기화만 영영 안 붙는다. 사용자에게는 "아이패드에 안 넘어오네" 로만 보이고, 개발자에게는 콘솔 로그 한 줄로만 보인다. 컴파일도 통과하고 기존 테스트도 전부 초록이다.

그래서 런타임에 기대지 않고 테스트로 못 박았다. CloudKit 을 띄우지 않고도 `Schema` 객체를 훑어 세 제약을 다 볼 수 있다 — 속성마다 `isUnique` 와 `defaultValue` 가, 관계마다 `isOptional` 과 `inverseName` 이 그대로 나온다.

작은 함정이 하나 더 있었다. **대상이 비면 루프를 도는 테스트는 그냥 통과한다.** 엔티티 목록을 못 읽어도 "unique 인 속성 없음"으로 초록이 뜬다. 그래서 루프 앞에 엔티티가 셋인지부터 단언해 두고, 진짜로 잡히는지 확인하려고 일부러 `@Attribute(.unique)` 를 하나 되살려 테스트가 빨개지는 걸 본 다음 되돌렸다. 경보가 울리는지 확인하지 않은 경보는 경보가 아니다.

## 열기에 실패하면 지우던 코드

원래 컨테이너 생성 코드는 실패하면 저장소 파일을 지우고 새로 만들었다. 데이터를 이관할 사용자가 없던 시절엔 합리적인 단순화였다.

동기화가 붙은 다음에는 그 동작이 전혀 다른 뜻이 된다. 엔타이틀먼트 하나가 빠졌거나 기기가 iCloud 에서 로그아웃됐을 뿐인데 **사용자의 플랜을 전부 지우게 된다.** 여는 순서를 다시 짰다 — iCloud 로 열기, 안 되면 로컬 전용으로라도 열기, 그것도 안 될 때에야 지우기. 동기화가 안 붙는 것보다 데이터가 사라지는 쪽이 비교할 수 없이 나쁘다.

## 알람이 두 번 울린다

배치가 두 기기에 깔리면 두 기기가 각자 알람을 예약한다. 같은 일정이 아이폰과 아이패드에서 동시에 울린다는 뜻이다. 앱이 몰래 "주 기기"를 고르는 방법도 있지만, 그러면 안 울리는 쪽에서 왜 안 울리는지 알 길이 없다.

설정에 스위치를 하나 뒀다. 기본은 켜짐이라 기기가 한 대인 사람에게는 아무것도 달라지지 않고, 끄면 그 기기에 이미 걸려 있던 예약까지 걷힌다.

![설정 시트. 동기화 구역에 iCloud 상태가 읽기 전용으로 있고, 알람 구역 맨 위에 '이 기기에서 알람 울리기' 스위치가 있다](/blog/planner-icloud-sync/sync-and-alarm-settings.png)

설정값 자체도 같은 질문을 받았다 — 이건 사람을 따라야 하나, 기기를 따라야 하나. 시간 표기나 기본 배치 길이는 사람을 따라간다. 반면 지금 보고 있는 프로필은 기기를 따라야 한다. 아이폰으로는 "회사", 아이패드로는 "공부"를 펴 놓고 싶을 수 있으니까. 그래서 설정은 iCloud 공용과 기기별 두 자리로 갈렸다.

## 남은 것

코드는 다 올라갔지만 동기화가 실제로 도는 데는 손으로 할 일이 남아 있다. 개발자 포털에서 iCloud 컨테이너를 만들고 **그것을 App ID 에 붙이는 것**(만들기와 붙이기는 별개의 동작이고, 붙이지 않으면 배포 빌드가 코드 서명에서 죽는다 — 뒤에 여섯 번 겪었다), 그리고 실기기로 한 번 돌려 개발 스키마가 생긴 뒤 CloudKit 콘솔에서 **프로덕션으로 배포**하는 것. 두 번째를 빼먹으면 개발 빌드만 동기화되고 TestFlight 빌드는 똑같은 코드로도 조용히 안 된다. 이 기능은 처음부터 끝까지 "조용히 안 되는" 실패 모드로 가득하다.

## 2026-09-23 — 이 글이 쓰여진 날부터 동기화는 한 번도 붙지 않았다

위에서 "두 기기가 같은 플랜을 본다" 고 썼는데, 사실이 아니었다. 코드는 올라갔고 화면은 멀쩡했고 제약을 지켰다고 믿었지만, 미러링은 켠 날부터 **한 번도 붙은 적이 없다.**

제약 표의 셋째 줄이 틀렸기 때문이다. CloudKit 이 실제로 거절할 때 하는 말에는 to-one 이라는 단서가 없다.

```
CloudKit integration requires that all relationships be optional, the following are not:
Profile: todos
Todo: blocks
```

`Profile.todos` 와 `Todo.blocks` 는 to-many 라서 `[Todo] = []` 로 그냥 두었다. 그 둘 때문에 컨테이너가 안 열렸고, 위에서 자랑스럽게 써 둔 3단 폴백이 설계대로 조용히 로컬 전용으로 받아 냈다. 침묵이 제 일을 너무 잘했다.

### 틀린 규칙은 그걸 지키는 테스트까지 틀리게 만든다

이 글에서 "런타임에 기대지 않고 테스트로 못 박았다" 고 했다. 그 테스트는 이렇게 생겨 있었다.

```swift
#expect(relationship.isOptional || relationship.isToOneRelationship == false, …)
//                              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ to-many 를 빼 준다
```

규칙 문장이 "to-one 관계는" 이었으니 테스트도 to-many 를 면제했다. 잘못된 문장 하나가 코드와 검사 양쪽에 똑같이 복사된 것이다.

위에서 "경보가 울리는지 확인하지 않은 경보는 경보가 아니다" 라고 썼는데, 이번 건은 그보다 나쁘다. 경보는 제대로 울렸다 — 감시 구역 **밖**에서 일어난 일이었을 뿐이다. 울려 보는 것으로는 안 잡힌다. 경보가 무엇을 안 보고 있는지를 따로 물어야 잡힌다.

### 원인을 좁히는 데 하루가 걸린 이유

침묵을 설계했으면 그 침묵을 깰 열쇠도 같이 만들어야 했는데, 그걸 안 했다. 실패를 잡는 자리는 이랬다.

```swift
AppLog.error(.data, "cloudkit mirroring unavailable — opening local-only store")
```

오류 객체는 받아서 `도메인#코드` 로 접어 버렸다. 로그에 이유가 한 글자도 없다. `NSCocoaErrorDomain#134060` 으로는 "스키마가 걸렸다" 와 "엔타이틀먼트가 없다" 가 구분되지 않는다. 그래서 엔타이틀먼트, 프로비저닝 프로파일, 모델 제약을 전부 손으로 훑고 나서야, **이유를 로그에 남기는 PR 을 먼저 하나 띄웠다.** 그걸 기기에 올리고 5초 만에 원인이 나왔다.

이유는 이제 두 겹으로 남는다. `도메인#코드` 는 어디서나, 오류 전문은 디버그 빌드에서만. 전문에는 저장소 파일 경로 같은 게 섞이니 배포 빌드의 크래시 리포트로는 보내지 않는다.

### TestFlight 로는 확인할 수 없는 일이었다

이 글 맨 아래에 "실기기로 한 번 돌려 개발 스키마가 생긴 뒤 프로덕션으로 배포" 라고 적어 뒀는데, 그 사이에 순서가 하나 숨어 있다.

배포 서명 빌드는 CloudKit **프로덕션** 환경을 본다. 프로덕션에서는 레코드 타입이 자동으로 안 생긴다. 그러니 TestFlight 빌드만 돌리면서 콘솔의 개발 스키마가 차기를 기다리면 영원히 안 찬다 — 개발 스키마를 만드는 건 개발 서명 빌드뿐이고, 프로덕션 스키마를 만드는 건 콘솔의 배포 버튼뿐이다. 기기 개발 빌드가 프로비저닝에서 막히면 시뮬레이터로 우회하면 된다. 시뮬레이터는 프로파일을 안 쓰고, CloudKit 은 개발 환경으로 정상 동작한다.

### 고치고 나서

관계 둘을 옵셔널로 바꾸고, `?? []` 가 열 자리에 흩어지지 않도록 nil 을 접는 접근자를 모델에 뒀다. 테스트의 면제 조항은 없앴고, 관계가 넷인지부터 단언하게 했다.

옵셔널리티가 바뀌면 Core Data 버전 해시가 바뀐다. 기존 저장소가 안 열리면 3단 폴백의 마지막 단이 사용자 데이터를 지운다는 뜻이다. 그래서 이론으로 넘기지 않고 시뮬레이터에 옛 빌드를 깔아 저장소를 만든 다음 새 빌드를 그 위에 덮었다. 옛 빌드는 위의 오류를 뱉고, 새 빌드는 오류도 재생성도 없이 열리며 행이 그대로 남는다. 경량 마이그레이션으로 덮인다.

이제 남은 건 처음부터 남아 있던 그 한 줄이다 — 개발 빌드로 한 번 써서 개발 스키마를 만들고, 콘솔에서 프로덕션으로 배포하기.

## 이력

- 2026-09-21 — 계정 없이 CloudKit 으로 두 기기를 묶고, 스키마 제약 셋을 테스트로 못 박았다.
- 2026-09-23 — 그 제약 문장이 틀렸다는 걸 알았다. to-many 관계도 옵셔널이어야 한다. 규칙·테스트·삼킨 오류 로그를 함께 고쳤다.
