시간표 앱의 캘린더를 이제 파일로 보낼 수 있다. 캘린더 `…` › 공유 › 파일로 내보내기를 누르면 캘린더 전체가 `.supertimetable` 파일 하나로 나가고, 받은 사람이 파일을 열면 자기 캘린더로 들어와 바로 열린다.

> 2026-11-18: 아래의 zip 형식은 하루 만에 철회했다. 지금 앱이 내보내는 파일은 다시 JSON 하나다. 무엇을 왜 뒤집었는지는 맨 아래 절에 있고, 그 위의 글은 11월 17일의 판단을 그대로 남긴 것이다.

## 같은 파일, 안이 바뀌었다

예전 `.supertimetable` 은 시간표 하나를 그대로 적은 JSON 이었다. 11월 17일 판은 이것을 zip 으로 바꿨다. 안에는 목차 한 장과 문서가 들어 있다.

| 안의 파일 | 내용 |
|---|---|
| `manifest.json` | 이 파일의 형식 이름 · 판 번호 · 문서 목록(종류와 위치, 순서대로) |
| `timetables/<id>.json` | 시간표 하나 — 예전 공유 파일과 똑같은 JSON |
| `calendars/<id>.json` | 캘린더 하나 — 앱이 기기에 저장하는 캘린더와 똑같은 JSON |

확장자도, 파일을 눌렀을 때 앱이 뜨는 방식도 그대로다. 앱은 파일의 첫 네 바이트를 보고 zip 이면 새 형식으로, 아니면 예전 JSON 으로 읽는다. 그래서 예전에 받아 둔 시간표 파일은 지금도 열린다.

그동안 캘린더에도 "파일로 내보내기" 메뉴가 있긴 했다. 눌러 보면 지금 보고 있는 **한 주**를 시간표 파일로 내보내고 있었다. 반복 일정의 나머지 주, 따로 옮겨 둔 회차, 날짜 메모는 다 빠졌다. 이제는 캘린더 문서 전체가 나간다.

## JSON 에 종류 표시만 더하면 안 됐다

처음 떠올린 건 가장 작은 변경이었다. 캘린더 JSON 맨 위에 `"type": "calendar"` 를 하나 더해 같은 확장자로 내보내는 것이다. 이 길이 진 이유는 이틀 전의 다른 결정에 있다. 캘린더 저장 키를 시간표와 같은 이름으로 맞춰 두었다 — `schedules`, `startDayOfWeek` 처럼. 그래서 `type` 을 모르는 옛 앱이나 Android 앱이 이 파일을 열면 거절하지 않는다. **이상한 시간표 하나로 받아들인다.** 반복 규칙은 사라지고 일정은 엉뚱한 요일에 앉는다. 조용히 엉뚱하게 읽히는 쪽이 "열 수 없음" 보다 나쁘다.

다른 두 안도 견줬다.

- **JSON 봉투 하나** (`{"documents": [...]}`) — 옛 앱이 시간표 이름 키를 못 찾아 거절하는 건 zip 과 같다. 하지만 시리즈 수 상한을 없앤 캘린더는 커질 수 있다. 통째로 읽어야 하고, 문서 하나씩 크기 상한을 걸기도 어렵다.
- **캘린더 전용 확장자** (`.supercalendar`) — 파일 종류를 하나 더 등록해야 하고, Android 쪽 "연결 프로그램" 필터도 한 벌 더 깔아야 한다. 그 필터는 이미 기기마다 따로 맞추느라 몇 번을 고친 자리다.

zip 은 옛 앱이 "이 파일을 열 수 없음" 으로 깨끗하게 거절한다. 시간표와 캘린더를 한 파일에 같이 담을 수 있고, 안의 내용은 예전 JSON 그대로라 디코더도, 깨진 파일을 거절하는 규칙도 새로 만들지 않았다. 바뀐 건 껍데기뿐이다.

## 남이 보낸 zip 을 믿지 않는 법

받은 파일은 남이 만든 것이다. 그래서 읽는 순서를 정했다.

1. zip 끝의 목록(중앙 디렉터리)만 먼저 읽는다. 파일은 64MB, 항목은 64개, 항목 하나는 32MB 까지다. 넘으면 **풀기 전에** 거절한다.
2. 풀고 나서 실제 크기가 목록에 적힌 크기와 다르면 거절한다. 작게 적어 놓고 크게 풀리는 파일이 여기서 걸린다. CRC 도 대조한다.
3. 문서 하나라도 일부가 깨져 있으면 묶음 전체를 거절한다. 일부만 들어오면 받은 사람은 무엇이 빠졌는지 모른다.
4. 시간표 20개, 캘린더 20개 상한에 다 못 들어가면 하나도 넣지 않는다.

zip 은 외부 라이브러리 없이 직접 짰다. 쓰기는 압축 없이(stored) 고정 시각으로 해서 같은 내용이면 같은 바이트가 나온다. 읽기는 Android `ZipOutputStream` 이 쓰는 deflate 도 받는다. 풀기는 시스템 `Compression` 프레임워크가 한다.

## 대가와 지금 상태

**옛 버전 앱은 새 파일을 못 연다.** 받는 쪽이 업데이트해야 한다(이 대가가 다음 날 결정을 뒤집은 이유가 됐다). 시간표 공유까지 지금 바꿀지, 캘린더만 새 형식으로 낼지 골라야 했는데, 형식이 두 갈래로 오래 남는 쪽을 피했다. 그래서 Android 도 같은 날 같은 형식으로 바꿨다. Android 에는 그날 아직 캘린더가 없어서 묶음의 시간표만 들였다(지금은 캘린더도 들인다).

같은 날 캘린더 하나의 일정 시리즈 500개 상한도 없앴다. 저장소를 SQLite 로 옮겨 편집 하나가 바뀐 줄 하나만 쓰게 된 뒤라 가능했다. 캘린더는 시간이 갈수록 쌓이는 문서라 500 은 몇 년 쓰면 닿는 벽이었다. 실기기 AirDrop 과 Mac 에서 주고받기는 아직 해 보지 않았다.

## 2026-11-18 — zip 을 철회하고 JSON 하나로 되돌렸다

하루 뒤에 질문 하나가 들어왔다. 표준 캘린더 파일인 `.ics` 도 속이 zip 이냐는 것이다. 아니다. `.ics` 는 압축도 색인도 없는 텍스트 하나다. 일정이 수천 개여도 몇 MB 고, 반복 일정은 회차를 풀지 않고 규칙 한 줄로 적는다. 캘린더 앱들은 이 파일을 주고받을 때 한 번 통째로 읽고, 평소에는 제 데이터베이스를 쓴다.

우리 공유 파일도 처지가 같다. 문서 하나를 담고, 받을 때 한 번 통째로 읽는다. zip 을 고르며 적은 이유 가운데 "커지면 항목 단위로 골라 읽기" 는 실제로 쓸 일이 없었다. 일정이 늘어도 빨라야 하는 곳은 기기 안 저장소고, 그건 SQLite 로 옮기면서 이미 풀었다. 반면 대가는 컸다. 캘린더와 무관한 **시간표 파일까지** 옛 앱이 못 열게 됐다.

그래서 zip 을 걷었다. 지금 파일은 둘 다 JSON 하나다.

| 파일 | 지금 나가는 내용 | 옛 앱이 열면 |
|---|---|---|
| 시간표 | 11월 17일 전과 같은 JSON, 바이트까지 같다 | 그대로 열린다 |
| 캘린더 | `{"documentType": "calendar", "calendar": { … }}` | "파일을 열 수 없음" |

캘린더 쪽은 한 번 더 고쳤다. 처음에는 캘린더 JSON 맨 위에 표식만 하나 더했다. 그러자 위에서 걱정한 일이 그대로 일어났다. 캘린더의 키가 시간표와 이름도 자리도 같아서, 표식을 모르는 옛 앱이 이 파일을 주간 시간표로 들였다. 하루짜리 일정까지 매주 일정이 되고, 받은 사람은 그게 캘린더였다는 걸 알 길이 없다. 못 여는 것보다 나쁘다는 17일의 판단은 맞았다. 틀린 건 그 해법으로 zip 까지 간 것이다.

필요한 건 봉투 한 겹이었다. 캘린더 본문을 `calendar` 키 아래로 내리면 맨 위에는 시간표가 찾는 키가 하나도 없다. 옛 앱은 시간표 이름조차 못 찾고 깨끗하게 거절한다. 새 앱은 표식을 보고 안쪽을 캘린더로 읽는다. 17일에 이 안을 버린 이유는 "통째로 읽어야 한다" 였는데, 어차피 통째로 읽는 파일이었다.

zip 을 읽는 코드도 같이 지웠다. 이틀 사이의 시험 빌드가 만든 파일은 이제 열리지 않는다. 그 파일을 위해 남의 zip 을 검사하는 코드를 계속 들고 가는 것보다 다시 내보내는 쪽이 싸다고 봤다. iOS 와 Android 를 같은 날 같은 형식으로 바꿨다.

옛 앱이 정말 거절하는지는 테스트 하나가 대신 본다. 내보낸 캘린더 파일을 시간표 읽기 함수에 그대로 넣어 실패하는지 확인한다. 캘린더 파일 맨 위에 시간표 키를 더하면 이 테스트가 깨진다. 실제 스토어판 앱으로 열어 보는 일은 아직 남았다.

배운 건 순서다. 컨테이너를 바꾸기 전에 "지금 형식으로 못 하는 일이 실제로 있나" 를 먼저 적었어야 했다. 적어 봤다면 없었다.

## 이력

- 2026-11-17 — 캘린더 파일 공유를 넣으면서 공유 파일을 zip 묶음으로 바꿨다
- 2026-11-18 — zip 을 쓰기 · 읽기 모두 철회하고 JSON 하나로 되돌렸다. 캘린더 파일은 옛 앱이 거절하도록 본문을 `calendar` 키 아래에 싣는다
