일정 색이나 제목을 바꾸고 ✓ 를 누르면, 같은 색·제목의 일정이 더 있을 때 "함께 바꿀까요" 를 묻는 작은 시트가 뜬다. 이 시트가 이제 ✓ 버튼에서 자라 나오고, X 로 닫으면 다시 ✓ 로 줄어든다. 방금 누른 버튼과 뜬 시트가 같은 물건으로 보인다.

## 반 높이 시트의 아래 절반이 비어 있었다

고치기 전 시트는 제목, 전/후 블록 두 개, 설명 한 줄, 버튼 둘이 위쪽에 몰려 있고 아래 절반이 비었다. 좌상단 X 는 직접 그린 36pt 원이라 뒤에 보이는 편집 시트의 X 보다 눈에 띄게 작았다.

![일괄 변경 시트 — 전/후 블록이 남는 높이를 채우고, X 는 편집 시트의 X 와 같은 크기다](/blog/timetable-batch-confirm-zoom/sheet-settled.png)

세 가지를 바꿨다.

| | 전 | 후 |
|---|---|---|
| 뜨는 방식 | 아래에서 올라옴 | ✓ 버튼이 커지며 시트가 됨 |
| X | 직접 그린 36pt 원 | 툴바 버튼 (다른 시트와 같은 것) |
| 빈 아래쪽 | 그대로 빔 | 전/후 블록이 남는 높이를 채움 |

X 는 크기를 44pt 로 키우는 대신 시트를 `NavigationStack` 으로 감싸고 툴바의 취소 자리에 넣었다. 크기만 맞추면 유리 재질이 또 다르다. 같은 시스템 버튼을 쓰면 맞출 것이 없다.

빈 곳은 시트를 낮춰서 없애지 않았다. 이 앱은 내용 높이를 재서 시트 높이를 맞추는 장치를 하루 전에 전부 걷어냈다(내용이 바뀔 때마다 시트가 움직였다). 대신 내용 중 "그림" 인 전/후 블록에 `maxHeight: .infinity` 를 줬다. 시간표의 일정 블록은 원래 세로로 길어서, 키워 놓으니 오히려 그리드의 블록과 닮았다.

## 줌 전환은 두 줄이다

iOS 26 은 시트가 버튼에서 자라 나오는 전환을 준다. 출발 버튼에 `matchedTransitionSource(id:in:)`, 시트 내용에 `navigationTransition(.zoom(sourceID:in:))`. 툴바 항목(`ToolbarItem`)에도 같은 수식어가 붙는다.

![✓ 버튼이 커지며 시트가 되는 네 프레임](/blog/timetable-batch-confirm-zoom/zoom-open.png)

돌아가는 길도 시스템이 한다. X 를 누르든 쓸어내리든 시트가 ✓ 로 줄어든다. 직접 만든 `matchedGeometryEffect` 오버레이로도 비슷한 그림은 나오지만, 그러면 딤·쓸어내리기·키보드를 전부 손으로 맞춰야 한다.

## 저장하면 ✓ 만 그리드 위에 남았다

이 시트의 두 버튼("함께 변경", "이 일정만")은 확인 시트만 닫는 게 아니라 아래 편집 시트까지 한 번에 내린다. 줌 전환을 붙이고 그 길을 녹화해 보니 이랬다.

![저장으로 닫힐 때 — 편집 시트는 내려가는데 확인 시트가 ✓ 로 줄어 그리드 위에 떠 있다](/blog/timetable-batch-confirm-zoom/save-ghost.png)

확인 시트는 약속대로 ✓ 로 돌아가려 한다. 그런데 그 ✓ 가 달린 편집 시트는 이미 내려가는 중이다. 시트는 ✓ 가 **있던 자리**를 향해 줄어들고, 0.2초쯤 검은 ✓ 원 하나가 시간표 위에 혼자 떠 있다가 사라진다.

처방은 저장으로 닫히는 길에서만 줌 복귀를 끄는 것이다. `sourceID` 를 상태로 두고, 두 저장 버튼이 닫기 직전에 짝이 없는 id 로 바꾼다. 돌아갈 출발점을 못 찾은 시트는 ✓ 로 변하지 않고 편집 시트와 함께 내려간다. X 와 쓸어내리기는 그대로 ✓ 로 돌아간다.

스크린샷으로는 이걸 못 본다. UI 테스트의 탭은 화면이 정착할 때까지 기다린 뒤 다음 줄로 넘어가서, 탭 직후에 찍은 다섯 장이 전부 정착한 그림이었다. 시뮬레이터 화면 녹화를 켜 놓고 테스트를 돌린 뒤 30fps 로 프레임을 펼쳐야 보인다. 열림, X 닫힘, 저장 닫힘 세 구간을 따로 본다.

덤으로 하나. 줌이 도는 동안 출발 버튼은 화면에서도 접근성 트리에서도 사라진다. 시트가 떠 있을 때 ✓ 버튼의 프레임을 묻는 테스트는 실패한다.

## 지금 상태

아이폰에서는 세 구간 모두 프레임으로 확인했다. 아이패드의 편집 팝오버 ✓ 에도 같은 출발점을 걸어 뒀지만 거기서는 아직 찍어 보지 않았다.

## 2026-10-09 밤 — "함께 변경" 을 누르면 이전 블록이 이후 색으로 바뀌었다

전/후 블록을 키워 놓고 나니 다른 것이 보였다. "함께 변경" 을 누르면 시트가 내려가는 동안 왼쪽의 이전 블록이 오른쪽과 같은 색, 같은 제목으로 바뀐다. 두 블록이 똑같은 그림이 된 채 닫힌다. "이 일정만" 으로 닫으면 멀쩡하다.

닫는 호출은 닫힘 애니메이션을 시작할 뿐이다. 시트 내용은 다 내려갈 때까지 화면에 있고, 읽고 있는 `@State` 가 바뀌면 그 프레임에 다시 그려진다. "함께 변경" 은 저장한 뒤 "원래 스타일" 변수를 방금 저장한 스타일로 갈았다. 스타일이 바뀌었는지 판정하는 기준값이니, 저장했으면 따라오는 게 맞다. 문제는 이전 블록이 그 변수를 그대로 그리고 있었다는 것이다. 비교 화면의 "이전" 과 변경 감지의 기준은 같은 값이라 한 변수를 나눠 쓰게 되는데, 하나는 저장하면 움직여야 하고 하나는 움직이면 안 된다.

이전 블록이 그리는 값을 따로 뒀다. ✓ 를 누르는 순간 원래 스타일을 한 번 찍고, 시트는 그 사본만 그린다. 기준값은 언제 바뀌어도 그림이 안 따라간다. 기준값을 가는 줄을 지워도 지금은 고쳐지지만, 그림이 기준을 직접 읽는 구조가 남으면 그 줄이 다시 생기는 날 같은 증상이 돌아온다. 갱신을 닫힌 뒤로 미루는 타이머는 닫힘 길이에 기대는 것이라 쓰지 않았다.

이 줄은 반년 전부터 있었다. 저장 로직 테스트는 어느 일정에 무엇이 저장되는지만 봤고, 줌 전환을 붙이며 프레임을 펼쳐 볼 때도 ✓ 가 남는지만 봤다. 닫으면서 저장하는 버튼을 만들 때는 그 버튼이 바꾸는 상태와 닫히는 창이 그리는 상태를 겹쳐 본다. 이번 수정은 소스 계약 테스트로 묶었고, 닫힘 구간을 다시 녹화하지는 않았다.

## 이력

- 2026-10-09 저녁 — ✓ 에서 자라 나오는 줌 전환, 툴바 X, 전/후 블록이 남는 높이를 채움
- 2026-10-09 밤 — 저장으로 닫힐 때 이전 블록이 이전 스타일 그대로 남게
