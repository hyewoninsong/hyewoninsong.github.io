시간표를 잠그면 한눈에 보이도록 줄어들고, 풀면 끌기 좋게 1.5배로 늘어난다. 이 전환이 "약간 버벅여서 완성도가 떨어져 보인다" 는 말을 들었다. 지금은 잠금 버튼을 누른 다음 프레임부터 60fps 로 움직인다.

## 곡선도 좌표도 맞았는데 프레임이 빠졌다

이 줌은 이미 두 번 고친 자리다. 처음에는 그리드 높이와 스크롤 위치가 서로 다른 곡선으로 움직여 화면이 튀었고, 두 번째는 스크롤 한계를 `contentInset` 으로 재서 맨 아래에서 36pt 가 홱 끌려 올라갔다(`adjustedContentInset` 이 맞다). 둘 다 영상을 프레임 단위로 뽑아 "라벨이 제자리에 그려졌는가" 를 봤다.

이번에는 자리가 다 맞았다. 그래서 영상 대신 박자를 쟀다. 줌이 도는 동안 `CADisplayLink` 틱이 몇 ms 간격으로 오는지, 토글 여섯 번을 찍었다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 줌 중 프레임 간격 | 26~67ms | 16~17ms |
| 잠금 버튼 → 줌 첫 프레임 | 120~130ms, 첫 토글은 500ms | 20~100ms |
| 하단 여백 | 0 → 160 → 19.8 → 0 | 0 고정 |

0.25초짜리 애니메이션이 여덟 장으로 그려지고 있었다. 60Hz 화면에서 절반이다.

## 툴바 버튼의 프레임이 1초 넘게 매 프레임 올라왔다

같은 로그에 다른 줄이 훨씬 많이 찍혀 있었다. 하단 툴바 버튼의 프레임이다.

블록을 끌 때 뜨는 시각 표시가 하단 버튼 뒤로 숨지 않도록, 버튼마다 `onGeometryChange` 로 화면 좌표를 재서 그리드 루트 뷰의 `@State` 에 모아 두고 있었다. 잠금을 풀면 툴바에 언두·리두·추가 버튼이 들어온다. iOS 26 툴바는 이걸 글라스 모프로 그린다. 버튼 폭이 5pt 에서 28pt 로, 위치가 몇 pt 씩 스프링으로 움직이고, 그 중간값이 전부 실측으로 올라온다. 토글 한 번에 38~44번이었다.

`@State` 가 바뀔 때마다 루트 뷰의 `body` 가 다시 돈다. 그 값은 환경값으로 내려가니 모든 일정 블록도 같이 돈다. 줌이 도는 바로 그 0.3초 내내 화면 전체를 프레임마다 다시 계산하고 있었던 것이다.

`onGeometryChange` 는 SwiftUI 가 보간하는 애니메이션에서는 최종값만 한 번 준다. 그래서 "실측은 가끔 오는 값" 이라고 여기기 쉽다. 툴바 모프는 UIKit 이 실제 레이아웃을 매 프레임 바꾸는 것이라 반대로 전부 온다.

## 새로 들어온 버튼은 창 밖 좌표로 먼저 재진다

하나가 더 있었다. 새로 생기는 버튼의 첫 실측이 `(-11, -11)` 이었다. 창에 붙기 전에 먼저 재진 값이다.

하단 여백은 "스크롤 뷰 바닥에서 가장 위에 있는 버튼 윗변까지" 로 계산한다. 윗변이 −11 이면 여백은 상한인 160 까지 튄다. 일정이 적어 화면을 채우도록 칸을 키워 그리는 시간표에서는 그 여백이 배율에도 들어간다. 줌이 시작되는 세 프레임 동안 배율이 1.47 → 1.10 → 1.42 → 1.47 로 바뀌었다. 그리드가 줄었다 늘면서 출발한 셈이다.

## 실측은 멈춘 뒤에만 뷰로 내보낸다

고친 건 한 줄이다. 버튼 프레임을 `@State` 대신 직접 만든 `@SettledState` 로 받는다. 쓰는 쪽은 최신 값을 그대로 읽고 쓰지만, 뷰가 읽는 값은 마지막 쓰기 뒤 0.15초 동안 조용했을 때 한 번만 바뀐다. 실측은 1pt 로 맞춰서 올린다. 모프가 끝날 때 소수점 둘째 자리가 한참 떨리는데, 그게 "멈춤" 을 미루지 않게 하려는 것이다.

다른 방법도 따져 봤다.

- **창 밖 좌표만 거른다.** 여백이 튀는 건 막지만 매 프레임 발행은 그대로라 프레임이 계속 빠진다.
- **잠금 토글 동안만 여백을 얼린다.** 여백은 고정되지만 `@State` 는 계속 바뀐다. 툴바 버튼이 바뀌는 다른 전환은 따로 막아야 한다.
- **선택한 블록이 없으면 프레임을 내려보내지 않는다.** 블록 쪽 계산은 줄지만 루트 뷰는 그대로 돈다.

대가도 있다. 잠금을 풀고 약 1초 동안은 시각 표시가 새 버튼 자리를 모른다. 그 1초 안에 블록을 골라 화면 맨 아래까지 끌어야 드러나는 틈이라 받아들였다.

## 위치와 박자는 따로 잰다

두 번을 고치면서 못 잡은 이유는 재는 방법에 있었다. 영상에서 프레임을 60fps 로 뽑으면 빠진 프레임은 같은 그림이 두 번 나올 뿐이라 눈에 띄지 않는다. 틱 간격은 예전에도 한 번 찍었는데, 그때는 UI 테스트로 버튼을 눌렀고 보이는 정지를 테스트 도구의 부하로 넘겼다. 이번에는 실행 인자를 주면 앱이 스스로 2초마다 잠금을 누르게 해서 쟀다.

수치는 시뮬레이터의 디버그 빌드에서 나온 것이다. 120Hz 실기에서 어떻게 느껴지는지는 다음 TestFlight 빌드에서 확인한다. 그리고 실기에서 다른 문제가 하나 더 나왔다 — 아래 11월 11일 절.

## 2026-11-11 — 박자는 맞췄는데, 순서가 엇갈리고 있었다

캘린더 주 보기에서 자물쇠를 풀고 잠그면 "일정 네모가 잔상이 생기며 줄어들고 늘어나고, 느린 느낌" 이라는 화면 녹화가 왔다. 이번엔 프레임이 빠진 게 아니었다. 녹화는 60fps 로 꽉 차 있었다.

![잠그는 동안 연속한 네 프레임 — 블록은 고르게 줄어드는데 두 번째에서 세 번째로 넘어갈 때 화면 전체가 아래로 튄다](/blog/timetable-lock-zoom-jank/zigzag-frames.png)

이번에도 눈으로 보지 않고 숫자로 쟀다. 블록이 있는 세로 한 줄만 영상에서 뽑아, 프레임마다 블록의 위·아래 끝이 몇 px 에 있는지 찍었다.

| | 프레임마다 |
|---|---|
| 블록 높이 | 904 → 876 → 819 → 783 → 752 — 한 방향 |
| 블록 윗변 | 741 → 777 → 852 → **834** → 883 → 930 → 1025 → **1005** |

크기는 맞게 변하는데, 위치가 몇 프레임마다 20~50px 거꾸로 돌아간다. 위치는 스크롤 오프셋이다. 줌이 도는 동안 보던 시각이 같은 자리에 머물도록, 매 프레임 콘텐츠 높이에서 진행도를 거꾸로 구해 오프셋을 다시 맞추는 코드가 있다. 첫 글에서 "같은 프레임에서 맞춘다" 고 고친 그 자리다.

그 "같은 프레임" 을 `CADisplayLink` 콜백으로 구현했던 게 문제였다. 디스플레이 링크는 같은 화면 주사에 불릴 뿐, SwiftUI 가 그 프레임의 애니메이션 값으로 레이아웃을 갱신하는 것보다 먼저일지 나중일지는 정해져 있지 않다. 링크가 나중이면 새 높이를 읽고 맞는 오프셋을 쓴다. 먼저면 지난 프레임의 높이로 오프셋을 맞추고, 곧이어 새 높이가 옛 오프셋과 함께 화면에 나간다. 순서가 프레임마다 엎치락뒤치락하니 화면이 한 프레임 늦었다 따라잡았다를 반복했고, 그게 잔상과 느림으로 보였다.

고친 건 박자를 거는 자리다. 스크롤 뷰의 `contentSize` 를 KVO 로 관찰해서, SwiftUI 가 높이를 쓴 바로 그 자리에서 오프셋을 맞춘다. 같은 트랜잭션이니 둘은 늘 같은 프레임에 나간다. 디스플레이 링크는 높이가 더 안 바뀔 때 끝내는 일만 남겼다. 시뮬레이터의 접힌 iPhone Duo 에서 같은 조작을 녹화하면, 고치기 전엔 첫 해제에서 아래 끝이 1429 → 1451 → 1411 → 1425 로 지그재그였고 고친 뒤엔 1373 → 1369 → 1365 → 1361 로 한 방향이다. 애니메이션 곡선은 건드리지 않았다. 느린 느낌은 곡선이 아니라 떨림에서 왔다.

지난번 교훈이 "위치와 박자는 따로 잰다" 였다면, 이번 것은 하나 더 붙는다. 위치를 잴 때도 그림을 넘겨 보지 말고 프레임마다 숫자로 적는다. 20px 짜리 한 프레임 역행은 눈으로 넘기면 보이지 않는다. 120Hz 실기 확인은 이번에도 다음 빌드에서 한다.
