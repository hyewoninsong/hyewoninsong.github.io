SuperFont 는 폰트를 프로파일로 묶어 Safari 와 설정 앱을 거쳐 설치한다. 단계가 많으니 어디서 사람들이 그만두는지를 원격으로 센다. 그 숫자를 콘솔에서 단계별·경로별로 쪼개 보려면 이벤트에 딸린 파라미터를 **지표로 등록**해야 하는데, 등록 화면을 열기 직전에 이름 하나가 걸렸다.

## 등록은 이벤트가 아니라 이름을 등록한다

파라미터를 맞춤 측정기준(문자열)이나 맞춤 측정항목(숫자)으로 등록할 때, 등록되는 것은 "이 이벤트의 이 파라미터" 가 아니라 **파라미터 이름 하나**다. 이벤트를 가리지 않는다. `count` 를 등록하면 `count` 를 보내는 모든 이벤트의 값이 그 하나에 들어간다.

코드에서는 이게 안 보인다. 이벤트를 열거형 하나로 묶어 두면 파라미터는 그 case 안의 필드처럼 읽히고, 이름이 짧을수록 읽기 좋아 보인다.

```swift
case .fontsRemovedFromApp(let count):
    return ["count": count]          // 앱에서만 제거한 항목 수 — 보통 한 자리
case .googleFontsListLoaded(let count):
    return ["count": count]          // 받아온 목록의 패밀리 수 — 1,800 쯤
```

두 줄 다 그 자리에서는 맞다. 합쳐 놓으면 한 지표가 "몇 개 지웠나" 와 "목록에 몇 개 있나" 의 합이 된다. 평균도 합계도 아무 뜻이 없고, 이벤트로 필터를 걸어도 지표 자체가 이미 두 분포의 합이라 갈라지지 않는다.

## 고칠 수 있는 창은 한 번뿐이다

여기서 급했던 건 버그의 크기가 아니라 **고칠 수 있는 시간**이었다.

- 등록은 **소급 적용되지 않는다.** 등록한 시점부터 쌓인다.
- 한 번 섞인 지표는 **되돌릴 수 없다.** 과거 데이터를 다시 나눠 담을 방법이 없다.
- 이름을 바꾸면 과거 이벤트와 **끊긴다.** 실사용 데이터가 쌓인 뒤에는 그 대가가 커진다.

SuperFont 는 아직 등록을 하나도 하지 않았고 시뮬레이터 실행은 애초에 수집에서 빼 두었으니, 잃을 게 거의 없는 지금이 유일하게 싼 시점이었다. 그래서 등록을 하기 전에 이름부터 고쳤다.

## 이벤트 이름 없이 읽히는가

기준은 하나로 정했다. **파라미터 이름은 이벤트 이름 없이 혼자 읽혀야 한다.** 콘솔의 지표 목록에는 이벤트가 같이 적히지 않기 때문이다.

- `count` → `removed_count` / `listed_family_count` — 두 이벤트가 같은 이름으로 다른 것을 세고 있었다
- `from`, `to` → `from_status`, `to_status` — 목록에 "from", "to" 로만 떠서는 무엇의 전이인지 알 수 없다
- `step` → `wizard_step` — 어느 흐름의 단계인지
- `context` → `error_context` — 이미 쓰던 크래시 쪽 키와도 이름이 맞는다
- `source` → `wizard_source` — 아래 참고

`source` 는 이유가 하나 더 있다. 구글 애널리틱스에는 **원래** 트래픽 소스를 뜻하는 기본 차원이 있어서, 같은 이름의 맞춤 차원을 만들면 콘솔에서 둘이 구분되지 않는다. 기본 차원과 겹치는 이름은 피하는 게 낫다.

반대로 **뜻이 같으면 이름을 일부러 공유한다.** `face_count` 는 프로파일을 열 때, 받아갈 때, 재설치할 때 세 이벤트가 전부 "서체 몇 개" 를 센다. 이건 사고가 아니라 이득이다 — 지표 하나만 등록하면 세 이벤트가 같이 커버된다. 공유가 문제가 되는 건 뜻이 다를 때뿐이다.

## 코드에 안 보이는 규칙은 테스트에 둔다

이 규칙의 고약한 점은 위반이 **코드 리뷰에서 보이지 않는다**는 것이다. 위의 두 줄은 각자 멀쩡하고, 잘못됐다는 사실은 콘솔에서, 그것도 데이터가 이미 섞인 다음에야 드러난다. 문서에 적어 두는 것으로는 부족했다.

그래서 이미 `print` 를 훑고 있던 계약 테스트에 한 줄을 더했다. 일반명 목록(`count`, `from`, `to`, `source`, `step`, `context`, `type`, `name`, `value`, `id`, …)에 든 이름을 파라미터 키로 쓰면 테스트가 떨어진다.

```swift
@Test func parameterKeysAreSelfDescribing() {
    for event in Self.samples {
        for key in event.parameters.keys {
            #expect(!Self.genericKeys.contains(key),
                    "'\(key)' 는 이벤트 이름 없이 뜻이 서지 않는다")
        }
    }
}
```

이 테스트는 이벤트를 추가할 때마다 대표값을 등록하게 하는 기존 규칙 위에 얹혔다. 새 이벤트를 만들면 자연히 이름도 같이 검사받는다.

## 옛 이름도 같이 등록했다

이름을 고치고 나서 그날 바로 등록까지 했다. 측정기준 13 개, 측정항목 12 개 — 그런데 그중 여섯은 **방금 버린 옛 이름**(`context`, `step`, `source`, `from`, `to`, `count`)이다.

이름을 바꾸면 옛 이름으로 올라간 데이터가 사라지는 게 아니라, **읽을 방법이 없어질 뿐**이다. 등록은 이름에 거는 것이니 옛 이름을 등록해 두면 개명 전 구간이 그대로 보고서에 뜬다. 앱은 더 이상 그 키를 보내지 않으니 새 데이터가 섞일 일도 없다. 설명란에 `legacy` 와 날짜를 적어 뒀고, `count` 에는 "두 뜻이 섞인 구간이라 합계·평균을 믿지 말 것" 을 적었다.

같은 이유로 "해석 가치가 낮다" 며 빼 두려던 것들도 결국 다 걸었다. 지금 볼 지표가 아니어도, 안 걸어 두면 나중에 필요해졌을 때 **그 기간이 통째로 빈다.** 한도가 각각 50 개라 아낄 이유가 없었다.

## 로그인이 막히는 자리

등록은 손으로 클릭하지 않고 Admin API 로 했는데, 여기서 한 번 막혔다. gcloud 로 애널리틱스 권한을 얻으려 하면 구글이 **"차단된 앱"** 화면을 띄운다. gcloud 의 기본 OAuth 클라이언트가 애널리틱스 같은 민감 스코프로는 검증돼 있지 않아서다. 재시도로는 안 뚫린다.

우회는 서비스 계정이다. 프로젝트에 서비스 계정을 하나 만들고, 애널리틱스 속성의 **액세스 관리**에서 그 계정을 편집자로 초대하면 동의 화면 자체가 필요 없다. 권한을 클라우드 쪽이 아니라 애널리틱스 쪽에서 준다는 게 핵심이다.

## 지금 상태

이름과 등록이 모두 끝났고, 다음 빌드가 실기에 올라가는 순간부터 새 이름으로 쌓인다. 소급이 안 되는 지표는, 세기 시작하지 않으면 영영 없는 숫자다.

## 2026-09-26 — 퍼널은 모든 단계가 가진 축으로만 나뉜다

출시 전에 등록 목록을 한 번 더 대조했다. 코드가 보내는 파라미터 24개는 전부 콘솔에 있었다. 빠진 건 등록이 아니라 **질문에 답이 나오는지**였다.

가장 알고 싶은 숫자는 "Google Fonts 로 들어온 사람은 몇 %가 설치를 마치는가" 다. 그래서 `wizard_source` 를 위저드 시작과 단계 도달 이벤트에 실어 뒀다. 그런데 퍼널 탐색에서 세그먼트를 걸어 보면 **시작만 갈리고 끝은 안 갈렸다.** GA4 의 퍼널은 모든 단계가 공통으로 가진 측정기준으로만 쪼개진다. 정작 "설치가 끝났다" 를 말하는 이벤트 — 프로파일을 열었다, Safari 가 받아갔다, 설정 앱에서 등록된 걸 감지했다 — 는 위저드가 아니라 설치 세션이라는 다른 객체가 내고 있었고, 거기에는 경로가 없었다. "모든 단계에 실어라" 를 "위저드의 단계 이벤트에 실어라" 로 읽은 것이다.

같은 대조에서 하나가 더 나왔다. 내 폰트 탭에서 서체 하나를 다시 설치하는 시트는 위저드를 거치지 않고 설치 세션을 바로 부른다. 이 경로는 시작 이벤트 없이 퍼널 한가운데에서 튀어나오고, 시트의 "설정 열기" 는 착지 이벤트를 아예 내지 않았다. 흐름의 옆문이었다.

고친 건 단순하다. 설치 세션이 흐름 이름을 받아서 자기가 내는 네 이벤트 전부에 싣고, 설치 안내 화면의 세 이벤트도 같은 값을 읽는다. 옆문 두 개는 새 키를 만들지 않고 같은 축에 `reinstall_sheet`, `remove_sheet` 값으로 올렸다 — "이 이벤트가 어느 흐름의 것인가" 라는 뜻이 같으니 키를 나눌 이유가 없고, 나누면 세그먼트를 하나로 걸 수 없다. `install_route` 라는 새 키, `flow` 로 개명, 시트를 위저드에 합치기가 후보였는데 셋 다 계측 문제를 다른 곳에서 푸는 것이라 버렸다.

이번에도 규칙은 테스트에 뒀다. 설치 흐름에 속한 이벤트 열 개의 이름을 목록으로 고정하고, 그중 하나라도 `wizard_source` 가 없으면 떨어진다. 다음에 흐름에 이벤트를 하나 더 붙이는 사람은 목록에 이름을 넣기 전까지 빌드가 안 된다.

덤으로 두 가지를 더 걸었다. Safari 에서 아무것도 안 받고 돌아온 이벤트에 경과 시간을 실었다 — 130초면 서버가 먼저 죽은 것이고 4초면 "허용" 을 안 누른 것인데, 그동안은 둘이 한 숫자였다. 그리고 user property 를 처음으로 하나 만들었다. 지금 설치돼 있는 프로파일 수를 `0` / `1` / `2_5` / `6_plus` 로 접은 값인데, 이게 없으면 "설치를 한 번이라도 마친 사용자의 잔존율" 같은 세그먼트 자체를 만들 수 없다. 이벤트가 스무 개여도 user property 가 없으면 사용자는 한 덩어리다.

새로 보내는 키 세 개는 같은 날 등록하고 읽어서 확인했다. 등록 스펙은 이제 앱 저장소에 파일로 산다 — 다음 키를 추가하는 사람이 어디에 적고 무엇을 돌리는지 찾지 않아도 되게.

## 이력

- 2026-09-23 — 파라미터 이름은 앱 전체의 이름공간, 등록 전에 이름부터 고치고 옛 이름도 legacy 로 등록
- 2026-09-26 — 설치 흐름의 모든 이벤트에 경로 축, 옆문 두 개를 같은 축에, user property 첫 도입
