> 2026-10-24: 이 동기화는 사용자에게 한 번도 배포되지 못한 채 빠졌다. 사정은 맨 아래 섹션에 있다. 아래 본문은 그때 설계한 내용 그대로다.

MindPDF 는 아이패드에서 밑줄을 긋고 아이폰으로 그 밑줄만 다시 읽는 식으로 쓰던 앱이라, 두 기기가 서로 다른 걸 보여준다는 게 오래 걸렸던 흠이었다. 이 작업으로 같은 Apple 계정으로 로그인된 두 기기라면 밑줄, 마인드맵, PDF 원본이 서로를 따라간다. 한쪽에서 그은 밑줄이 다른 쪽에서도 그 자리에 있고, 맵에서 옮긴 노드도 넘어간다.

## 무엇이 바뀌었나

- 아이패드에서 그은 밑줄이 아이폰에도 뜬다. 반대도 된다.
- 맵에서 노드를 옮기거나 챕터를 합치면 다른 기기의 맵도 같은 모양이 된다.
- PDF 를 새로 가져오면 다른 기기에도 파일이 도착한다.

계정 화면도, 로그인도, 초대도 없다. 기기가 이미 로그인돼 있는 Apple 계정을 그대로 쓴다. SwiftData 를 CloudKit 개인 데이터베이스에 얹는 저장소 설정 한 줄이 전부다.

## 이번엔 이만큼만 — 왜 이렇게 갈랐나

**내 기기끼리만, 다른 사람과 공유는 아직 아니다.** CloudKit 에는 프로젝트 하나를 다른 사람에게 초대해 같이 편집하는 CKShare 도 있다. 그건 SwiftData 지원이 따로 필요하고, 초대 UI, 동시 편집 충돌, 참여자의 iCloud 용량 부담까지 딸려 온다. 지금 필요한 건 "내 아이폰에서 그은 게 내 아이패드에도 보이는 것" 뿐이라, 그 절반만 먼저 했다. 여러 사람이 함께 보는 기능은 여전히 보류다.

**PDF 는 iCloud Drive 파일이 아니라 별도 레코드(CKAsset) 로 옮긴다.** PDF 를 그냥 iCloud Drive 문서 폴더에 두는 방법도 있었다. 그러면 파일 하나가 그대로 클라우드에 있으니 간단해 보이지만, 다운로드 상태(내려받는 중/내려받음/자리만 있음)를 화면에 보여줘야 하고, 다른 프로세스가 같은 파일을 건드릴 때를 대비한 파일 조정(coordination)까지 앱이 떠안게 된다. 그 대신 PDF 바이트를 별도 레코드로 두고 CloudKit 이 동기화를 맡게 했다. 대가는 기기 안에 PDF 가 두 벌 있다는 것 — 화면이 여는 로컬 파일과, 스토어가 갖고 있는 외부 저장 바이트. iCloud 용량도 PDF 크기만큼 그대로 쓴다. 그래도 다운로드 상태 UI 와 파일 조정을 직접 짜는 것보다는 싼 대가라고 봤다.

**WebDAV 는 처음부터 후보에서 뺐다.** 예전에 검토했을 때 이미 나온 결론이다. WebDAV 는 업로드/다운로드 프로토콜이라 병합 개념이 없다. 스토어 파일을 WebDAV 에 올려 두고 두 기기가 열면 나중에 저장한 쪽이 앞의 걸 통째로 덮어쓴다.

## 트리는 CloudKit 이 모르는 개념이다

여기가 이번 작업의 진짜 난이도였다. CloudKit 은 필드 단위로 마지막에 쓴 게 이긴다. 그런데 마인드맵은 트리다. 트리 규칙(부모는 하나, 순환 없음, 형제 순서)은 CloudKit 레코드 하나에 들어 있는 게 아니라 레코드들 사이의 관계다.

구체적으로 이런 일이 난다. 아이폰에서 노드 A 를 B 밑으로 옮기고, 거의 동시에 아이패드에서 B 를 A 밑으로 옮기면 — 둘 다 각자 기기에서는 정상적인 편집이다. 합쳐지고 나면 A 의 부모가 B, B 의 부모가 A 인 순환이 생긴다. 이 상태에서 깊이(depth)나 서브트리 높이를 세는 코드는 부모를 계속 따라 올라가다 절대 끝나지 않는다. 형제 순서 번호가 겹치는 것, 두 기기가 각자 같은 챕터의 첫 밑줄로 챕터 노드를 하나씩 만들어 같은 챕터가 둘로 보이는 것도 같은 종류의 문제다 — CloudKit 은 "이 챕터 노드는 하나여야 한다" 는 걸 모른다.

그래서 합친 뒤에 도는 수리 단계를 따로 뒀다. 순환은 순환 안에서 가장 먼저 만들어진 노드를 최상위로 떼어 끊는다. 중복 챕터는 먼저 만들어진 쪽에 자식을 모으고 나머지를 지운다. 겹친 형제 순서는 (생성 시각, id) 순으로 다시 매긴다. 전부 **(생성 시각, id) 로만 정한다** — 그래야 두 기기가 각자 자기 데이터로 수리해도 같은 결론에 도달한다. 어느 한쪽이 정한 걸 상대가 다시 뒤집으며 주고받는 일이 없다는 뜻이다. 고칠 게 없으면 아무것도 쓰지 않는다.

수리 규칙에 예외를 하나 뒀다. 부모도 없고 프로젝트도 없는 노드는 건드리지 않는다. CloudKit 은 레코드가 순서 없이 도착하기 때문에, 지금 부모가 비어 있는 게 문제가 아니라 짝이 아직 오는 중일 수 있다. 여기서 지워 버리면 나중에 도착할 짝을 놓친 채 데이터를 잃는다.

밑줄은 이 문제를 아예 겪지 않는다. 밑줄은 트리가 아니라 독립된 레코드라서, 두 기기가 같은 문장에 겹쳐 그은 밑줄은 서로 다른 레코드로 둘 다 남는다. 겹쳐 보일 뿐 하나가 다른 하나를 지우지 않는다.

## 가는 길에 만난 함정 셋

**빈 배열 기본값이 있어도 to-many 관계는 CloudKit 이 필수로 거부한다.** `[T] = []` 처럼 기본값을 줬으니 괜찮을 거라 생각했는데, SwiftData 는 이걸 "기본값이 있는 필수 관계"로 만든다. CloudKit 은 관계는 무조건 옵셔널 타입(`[T]?`)이어야 통과시킨다. 저장하는 관계 이름을 옵셔널로 바꾸고, 옛 이름으로 된 non-optional 계산 프로퍼티를 그대로 남겨서 관계를 쓰는 수백 군데를 건드리지 않았다.

**앱에 iCloud entitlement 가 붙는 순간 테스트의 저장소까지 CloudKit 검사를 받는다.** `ModelConfiguration` 의 CloudKit 설정 기본값은 자동이라, entitlement 가 있으면 그걸 그대로 쓴다. 유닛 테스트는 앱을 호스트로 돌기 때문에, 메모리 저장소나 임시 파일 저장소도 전부 CloudKit 제약 검사를 받게 됐고, 그 제약을 모르는 옛 스키마로 저장소를 만드는 마이그레이션 테스트가 우르르 깨졌다. 테스트의 저장소 설정에는 CloudKit 을 쓰지 않는다고 항상 명시해 두는 걸로 고쳤다.

**동기화가 안 열리면 저장소를 옆으로 치우면 안 된다.** 원래 저장소가 안 열리면 파일을 옆으로 옮기고 새로 만드는 코드가 있었다. 계정 문제나 스키마 문제로 CloudKit 연결이 실패했을 뿐인데 이 코드가 그대로 돌면 사용자의 라이브러리를 통째로 치워 버린다. CloudKit 으로 안 열리면 먼저 동기화 없이 같은 파일을 로컬로 여는 단계를 끼워 넣었다. 로컬로도 안 열릴 때만 기존처럼 치운다.

## 남은 것 (2026-09-27 기준)

실기기 두 대로 아직 확인하지 못했다 — 시뮬레이터로는 CloudKit 동기화 자체를 볼 수 없다. CloudKit 콘솔의 개발 스키마를 프로덕션으로 배포하는 것도 아직이었다. 이 두 가지는 결국 하지 않았다 — 아래 섹션.

## 2026-10-24 — 4주 동안 빌드가 안 나간 이유, 그리고 동기화를 뺐다

동기화가 들어간 뒤로 TestFlight 배포가 매번 서명 단계에서 죽었다. 빌드는 3분쯤 돌다가 이렇게 끝난다.

```
Provisioning profile "iOS Team Provisioning Profile: *" doesn't include the iCloud capability.
Provisioning profile "iOS Team Provisioning Profile: *" doesn't include the Push Notifications capability.
```

앱은 iCloud 컨테이너와 푸시(CloudKit 이 변경을 알려 주는 통로)를 쓰겠다고 선언했는데, 개발자 포털의 앱 ID 에는 인앱 결제 하나만 켜져 있었다. 개발은 전부 시뮬레이터에서 했고 시뮬레이터 빌드는 서명을 보지 않으니, 그 차이가 배포 빌드에서야 드러났다. 앱 ID 에 없으니 새로 받은 배포 프로필에도 iCloud 가 없고, Xcode 는 맞는 프로필을 못 찾아 팀 와일드카드 프로필(`*`)로 떨어졌다. 메시지에 `*` 가 보이면 "이 앱 ID 로는 프로필이 안 맞는다"는 뜻이다.

배포 전 점검 스크립트는 이걸 봤다. 선언된 키 목록과 앱 ID 의 기능 목록을 나란히 출력까지 했다. 그런데 막지 않았다 — 승인이 필요한 몇몇 키만 막고 나머지는 "검토용으로 출력함" 으로 넘겼고, 프로필에 키가 아예 없는 경우는 비교 대상에서 빠졌다. 보는 사람이 없는 출력은 점검이 아니다. 지금은 iCloud·푸시·앱 그룹처럼 기능이 있어야 하는 키가 앱 ID 에 없으면 빌드 전에 막는다.

고치는 길은 있었다. 포털에서 iCloud 컨테이너를 만들어 앱 ID 에 붙이고(이 단계는 공개 API 에 없어 사람이 웹에서 해야 한다), 이 Mac 의 Xcode 에는 로그인된 계정이 없으니 배포 레인을 수동 서명으로 바꾸고, CloudKit 콘솔에서 운영 스키마를 배포하고, 실기기 두 대로 확인하는 것. 그 대신 동기화를 빼기로 했다. 지금 필요한 건 테스트 빌드가 다시 나가는 것이었고, 동기화는 아직 아무도 쓰지 못한 기능이었다.

뺀 범위는 이렇다.

- 저장소는 기기 안에만 연다. iCloud entitlement 와 원격 알림 백그라운드 모드도 뺐다. 이제 앱 ID 에 아무 기능이 없어도 서명된다.
- PDF 바이트를 스토어에 복사하던 일도 멈췄다. 기기 안에 PDF 가 두 벌 생기던 대가가 사라졌다.
- **스키마는 되돌리지 않았다.** CloudKit 에 맞춰 바꾼 모양(옵셔널 관계, 기본값, PDF 바이트 엔티티)은 그대로다. 되돌리면 마이그레이션이 하나 더 생길 뿐 얻는 게 없고, 다시 켤 때 그대로 쓴다.
- **트리 수리도 남겼다.** 맵을 열 때 깊이 제한과 함께 한 번 돌고, 고칠 게 없으면 아무것도 쓰지 않는다.

이번에 남긴 규칙 하나: 기능이 있어야 하는 entitlement 를 더하는 변경은 머지하기 전에 배포 빌드를 한 번 돌려 본다.
