시간표 앱이 저장 파일을 읽고 쓰는 길과 시각 기준·교시 기준 전환을 하루 동안 코드로 훑었다. 사용자 데이터가 아무 말 없이 바뀌거나 사라지는 길이 열한 개 나왔다. 크래시는 하나도 없었다. 전부 "성공" 으로 끝나는 실패라서 제보도 알럿도 없이 지나갔다.

## 사용자에게 달라진 것은 셋이다

**저장이 실패하면 알럿이 뜬다.** 저장 함수가 실패를 Bool 로 돌려주고 모든 호출부가 버렸다. 디스크가 꽉 찬 채 편집하다 앱을 끄면 그 세션이 전부 사라졌고, 화면은 끝까지 바뀐 대로 보였다. 이제 실패 연속마다 한 번 뜨고 저장이 다시 성공하면 내려간다. 실패마다 띄우면 편집 자체가 막히고, 배너는 멈추고 확인해야 하는 종류에 너무 조용하다.

**파일을 못 읽은 실행은 첫 실행이 아니다.** 저장 파일이 있는데 읽히지 않으면 먼저 위젯용 앱 그룹의 마지막 정상 저장본을 되읽는다. 매 저장이 같은 바이트를 두 곳에 쓰고 있었으니 한쪽은 다른 쪽의 백업인데, 아무도 되읽지 않았다. 그래도 못 살리면 "새 시간표로 시작했고 이전 파일은 따로 보관했다" 고 한 번 말한다. 빈 로드에서 저장을 아예 안 하는 안은 매 실행마다 같은 안내가 뜬다.

**전환 뒤 ✓ 는 되돌리기 한 번이다.** 시트에서 "교시 기준" 을 누르고 ✓ 를 누르면 알럿이 "되돌리기로 복구할 수 있습니다" 라고 약속했는데, 두 번 눌러야 시각형이었다. 중간 상태는 교시형인 채 지워진 일정이 마지막 교시에 포개져 되살아나는 그림이었다. 이제 첫 전환 전 스냅샷 하나만 언두에 등록하고 그 시트의 나머지 저장은 언두 없이 간다. `beginUndoGrouping` 을 탭에서 열고 ✓ 에서 닫는 안은 열린 묶음에 다른 창의 등록이 섞여서 버렸다.

## 성공으로 보이는 실패

나머지 일곱은 실패가 성공의 모양을 하고 있었다.

- **폴백은 손실이다.** 교시 목록이 깨진 파일은 시각형으로 열리면서 제보만 남겼다. 사본이 없어 다음 저장이 교시와 점심 자리를 영구히 지웠다. 제보는 빈도를 보는 도구고 사본은 되돌리는 도구다. 이제 파일 값과 다르게 여는 폴백은 전부 손실로 세어 원본을 격리한다.
- **카운터를 안 단 입구.** 같은 관대한 디코더를 파일 가져오기가 손실 카운터 없이 불렀다. 훅이 옵셔널이라 안 달아도 조용히 통과한다. `"schedules": "x"` 인 파일이 빈 시간표로 성공해 들어왔다. 가져오기는 되돌릴 사본이 없으니 통째로 거절한다.
- **빈 목록 = 첫 실행.** 못 읽은 파일의 빈 로드가 첫 실행 길로 가서 기본 시간표를 저장했다. 그 저장이 알람 동기화를 부르고, 기준이 메모리의 일정이니 빈 목록은 알람 전부 취소였다.
- **값 하나가 파일 전체를 막는다.** 분 값이 1440 을 넘으면 인코더가 throw 했다. `Codable` 은 중첩 값 하나의 throw 를 루트까지 올리므로 일정 하나가 모든 저장을 막았다. 값을 1440 으로 자르고 제보한다. 파일 거부는 값 하나를 잃는 것보다 나쁜 실패다.
- **사본이 한 벌.** `.backup` 과 `.corrupt` 가 종류별로 파일 하나였다. 새 버전 → 옛 버전 → 새 버전 왕복에서 유일한 원본 사본이 깎인 파일로 교체됐다. 이름에 스탬프와 시각을 넣고 다섯 벌까지 남긴다.
- **저장 값이 반복 횟수.** 알림 분의 자정 래핑이 `while total < 0 { total += 1440 }` 이었다. 저장본에 `1000000000000` 이 있으면 런치에서 수 분, `Int.max` 면 영원히 멎는다. 트랩이 아니라 멈춤이라 Crashlytics 에도 안 남는다. 상한 일주일, 계산은 나눗셈 한 번.
- **제보가 한 묶음.** 제보 지점 열다섯 개가 Crashlytics 코드 목록에 없어 전부 코드 0 으로 뭉쳤다. 소스를 읽는 계약 테스트가 미등록 지점을 잡는다.

## 축이 판정을 두 가지 쓰면 알럿이 셀 수 없다

9시부터 16시까지 7교시 시간표에 가져온 19:00 수업이 있다. 쉬는 시간을 0 에서 10분으로 바꾸고 ✓ 를 누르면 알럿은 삭제 0, 조정 0 인데 저장 값이 15:30 으로 옮겨 가고 알람도 따라갔다. 일정을 축에 굳히는 함수에는 "어느 칸과도 안 겹치는 일정은 그대로" 가드가 있었고, 규칙이 바뀔 때 같은 교시 자리로 옮기는 함수에는 없었다. 옮기는 함수가 그리기용 클램프를 타고 마지막 교시 한 칸을 저장했고, 알럿은 "옮긴 뒤 굳히면 달라지는 일정" 을 세니 옮기는 단계의 변화는 정의상 셈 밖이었다. 겹침 판정을 함수 하나로 모았다.

점심 칸을 켠 축에서 13:00–14:00 점심 칸 일정을 편집 시트로 열면 열자마자 블록이 5교시 앞 반까지 늘어나고, 알람만 바꿔 ✓ 해도 14:00–14:30 으로 저장됐다. 반 칸 인덱스는 "점심 칸이면 시작은 다음 교시, 끝은 앞 교시" 규칙만 있어 시작 8, 끝 7 로 뒤집혔고, `max` 가 그걸 8...8 로 접어 없는 칸을 지어 줬다. 뒤집힌 읽기는 접을 값이 아니라 "설명할 자리가 없다" 는 신호였다.

## 탭에 저장하고 ✓ 에 나머지를 저장하면

유형 전환은 라디오를 누르는 즉시 저장된다. 그리드가 저장된 타입에서 파생되기 때문이다. 교시에 안 들어가는 일정은 ✓ 에서야 세어 묻는다. 그 사이에 앱이 죽으면 다음 실행은 "교시형 + 실제 시각 일정" 모양만 보고 알럿도 언두도 없이 교시 시각으로 굳혔다. 확정을 기다린다는 사실은 그리드 뷰의 `@State` 에만 있었고, 뷰 상태는 프로세스와 함께 사라진다.

확정 대기를 시간표에 표식으로 저장하고, 표식이 남은 채 다시 실행되면 전환 전으로 되돌린다. 재실행이 "삭제 N개" 알럿을 다시 띄우는 안은 알럿 셈이 시트의 프리뷰 상태에 묶여 있어 그리드 밖에서 다시 만들어야 했고, 전환을 ✓ 까지 미루는 안은 처음 이유로 막혔다. 위의 "되돌리기 한 번" 도 같은 뿌리다. 누르는 자리와 확정하는 자리가 다르면 중간 상태가 파일에도 언두 스택에도 남는다.

## 왜 못 잡았나

각 변경은 제 테스트를 통과했다. 격리 테스트는 저장 층만 봤고 빈 로드를 받은 스토어가 무엇을 하는지는 묻지 않았다. 전환 테스트는 전환과 확정을 한 테스트 안에서 이어 불렀고, 둘 사이에 스토어를 다시 만드는 테스트가 없었다. "열고 ✓ 는 무손실" 을 확인한 수동 케이스는 전부 교시 안 일정이었다.

가정이 셋 있었다. 빈 목록은 첫 실행이라는 것, 저장 버전은 필드가 바뀔 때만 올린다는 것, 외부 파일 점검의 기대는 "트랩하지 않는다" 라는 것. 셋째는 "정해진 시간 안에 돌아온다" 로, 둘째는 "로드가 파일에 하는 일의 세대" 로 바꿔야 한다.

## 남은 것

열한 개가 각자 PR 로 들어갔고 각 PR 은 제 테스트만 돌렸다. 머지된 main 에서 전체 스위트를 한 번 돌리는 일이 남아 있다. 마지막 교시 뒤 밤 일정도 편집 시트를 열기만 하면 마지막 반 칸으로 들여지는데, 10월 9일 결정이 테스트로 고정하고 있어 따로 판단한다.
