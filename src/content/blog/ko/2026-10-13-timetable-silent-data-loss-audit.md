시간표 앱이 저장 파일을 읽고 쓰는 길과 시각 기준·교시 기준 전환을 하루 동안 코드로 훑었다. 사용자 데이터가 아무 말 없이 바뀌거나 사라지는 길이 열한 개 나왔다. 크래시는 하나도 없었다. 전부 "성공" 으로 끝나는 실패라서 제보도 알럿도 없이 지나갔다.

## 사용자에게 달라진 것은 셋이다

**저장이 실패하면 알럿이 뜬다.** 저장 함수가 실패를 Bool 로 돌려주고 모든 호출부가 버렸다. 디스크가 꽉 찬 채 편집하다 앱을 끄면 그 세션이 전부 사라졌고, 화면은 끝까지 바뀐 대로 보였다. 이제 실패 연속마다 한 번 뜨고 저장이 다시 성공하면 내려간다. 실패마다 띄우면 편집 자체가 막히고, 배너는 멈추고 확인해야 하는 종류에 너무 조용하다.

**파일을 못 읽은 실행은 첫 실행이 아니다.** 저장 파일이 있는데 읽히지 않으면 먼저 위젯용 앱 그룹의 마지막 정상 저장본을 되읽는다. 매 저장이 같은 바이트를 두 곳에 쓰고 있었으니 한쪽은 다른 쪽의 백업인데, 아무도 되읽지 않았다. 그래도 못 살리면 "새 시간표로 시작했고 이전 파일은 따로 보관했다" 고 한 번 말한다. 빈 로드에서 저장을 아예 안 하는 안은 매 실행마다 같은 안내가 뜬다.

**전환 뒤 ✓ 는 되돌리기 한 번이다.** 시트에서 "교시 기준" 을 누르고 ✓ 를 누르면 알럿이 "되돌리기로 복구할 수 있습니다" 라고 약속했는데, 두 번 눌러야 시각형이었다. 중간 상태는 교시형인 채 지워진 일정이 마지막 교시에 포개져 되살아나는 그림이었다. 이제 첫 전환 전 스냅샷 하나만 언두에 등록하고 그 시트의 나머지 저장은 언두 없이 간다. `beginUndoGrouping` 을 탭에서 열고 ✓ 에서 닫는 안은 열린 묶음에 다른 창의 등록이 섞여서 버렸다.

## 성공으로 보이는 실패

나머지 일곱은 실패가 성공의 모양을 하고 있었다.

- **폴백은 손실이다.** 교시 목록이 깨진 파일은 시각형으로 열리면서 제보만 남겼다. 사본이 없어 다음 저장이 교시와 점심 자리를 영구히 지웠다. 제보는 빈도를 보는 도구고 사본은 되돌리는 도구다. 이제 파일 값과 다르게 여는 폴백은 전부 손실로 세어 원본을 격리한다.
- **카운터를 안 단 입구.** 같은 관대한 디코더를 파일 가져오기가 손실 카운터 없이 불렀다. 훅이 옵셔널이라 안 달아도 조용히 통과한다. `"schedules": "x"` 인 파일이 빈 시간표로 성공해 들어왔다. 가져오기는 되돌릴 사본이 없으니 통째로 거절한다.
- **빈 목록 = 첫 실행.** 못 읽은 파일의 빈 로드가 첫 실행 길로 가서 기본 시간표를 저장했다. 그 저장이 알람 동기화를 부르고, 기준이 메모리의 일정이니 빈 목록은 알람 전부 취소였다.
- **값 하나가 파일 전체를 막는다.** 분 값이 1440 을 넘으면 인코더가 throw 했다. `Codable` 은 중첩 값 하나의 throw 를 루트까지 올리므로 일정 하나가 모든 저장을 막았다. 값을 1440 으로 자르고 제보한다. 파일 거부는 값 하나를 잃는 것보다 나쁜 실패다.
- **사본이 한 벌.** `.backup` 과 `.corrupt` 가 종류별로 파일 하나였다. 새 버전 → 옛 버전 → 새 버전 왕복에서 유일한 원본 사본이 깎인 파일로 교체됐다. 이름에 스탬프와 시각을 넣고 다섯 벌까지 남긴다.
- **저장 값이 반복 횟수.** 알림 분의 자정 래핑이 `while total < 0 { total += 1440 }` 이었다. 저장본에 `1000000000000` 이 있으면 런치에서 수 분, `Int.max` 면 영원히 멎는다. 트랩이 아니라 멈춤이라 Crashlytics 에도 안 남는다. 상한 일주일, 계산은 나눗셈 한 번.
- **제보가 한 묶음.** 제보 지점 열다섯 개가 Crashlytics 코드 목록에 없어 전부 코드 0 으로 뭉쳤다. 소스를 읽는 계약 테스트가 미등록 지점을 잡는다.

## 축이 판정을 두 가지 쓰면 알럿이 셀 수 없다

9시부터 16시까지 7교시 시간표에 가져온 19:00 수업이 있다. 쉬는 시간을 0 에서 10분으로 바꾸고 ✓ 를 누르면 알럿은 삭제 0, 조정 0 인데 저장 값이 15:30 으로 옮겨 가고 알람도 따라갔다. 일정을 축에 굳히는 함수에는 "어느 칸과도 안 겹치는 일정은 그대로" 가드가 있었고, 규칙이 바뀔 때 같은 교시 자리로 옮기는 함수에는 없었다. 옮기는 함수가 그리기용 클램프를 타고 마지막 교시 한 칸을 저장했고, 알럿은 "옮긴 뒤 굳히면 달라지는 일정" 을 세니 옮기는 단계의 변화는 정의상 셈 밖이었다. 겹침 판정을 함수 하나로 모았다.

점심 칸을 켠 축에서 13:00–14:00 점심 칸 일정을 편집 시트로 열면 열자마자 블록이 5교시 앞 반까지 늘어나고, 알람만 바꿔 ✓ 해도 14:00–14:30 으로 저장됐다. 반 칸 인덱스는 "점심 칸이면 시작은 다음 교시, 끝은 앞 교시" 규칙만 있어 시작 8, 끝 7 로 뒤집혔고, `max` 가 그걸 8...8 로 접어 없는 칸을 지어 줬다. 뒤집힌 읽기는 접을 값이 아니라 "설명할 자리가 없다" 는 신호였다.

## 탭에 저장하고 ✓ 에 나머지를 저장하면

유형 전환은 라디오를 누르는 즉시 저장된다. 그리드가 저장된 타입에서 파생되기 때문이다. 교시에 안 들어가는 일정은 ✓ 에서야 세어 묻는다. 그 사이에 앱이 죽으면 다음 실행은 "교시형 + 실제 시각 일정" 모양만 보고 알럿도 언두도 없이 교시 시각으로 굳혔다. 확정을 기다린다는 사실은 그리드 뷰의 `@State` 에만 있었고, 뷰 상태는 프로세스와 함께 사라진다.

확정 대기를 시간표에 표식으로 저장하고, 표식이 남은 채 다시 실행되면 전환 전으로 되돌린다. 재실행이 "삭제 N개" 알럿을 다시 띄우는 안은 알럿 셈이 시트의 프리뷰 상태에 묶여 있어 그리드 밖에서 다시 만들어야 했고, 전환을 ✓ 까지 미루는 안은 처음 이유로 막혔다. 위의 "되돌리기 한 번" 도 같은 뿌리다. 누르는 자리와 확정하는 자리가 다르면 중간 상태가 파일에도 언두 스택에도 남는다.

## 왜 못 잡았나

각 변경은 제 테스트를 통과했다. 격리 테스트는 저장 층만 봤고 빈 로드를 받은 스토어가 무엇을 하는지는 묻지 않았다. 전환 테스트는 전환과 확정을 한 테스트 안에서 이어 불렀고, 둘 사이에 스토어를 다시 만드는 테스트가 없었다. "열고 ✓ 는 무손실" 을 확인한 수동 케이스는 전부 교시 안 일정이었다.

가정이 셋 있었다. 빈 목록은 첫 실행이라는 것, 저장 버전은 필드가 바뀔 때만 올린다는 것, 외부 파일 점검의 기대는 "트랩하지 않는다" 라는 것. 셋째는 "정해진 시간 안에 돌아온다" 로, 둘째는 "로드가 파일에 하는 일의 세대" 로 바꿔야 한다.

## 남은 것

파일 앱에서 격리본과 백업 사본을 꺼낼 길이 아직 없다. 알럿은 "앱 문서 폴더에 따로 보관" 이라고만 말한다. 파일 공유를 켜고 가져오기가 저장 파일 묶음도 받게 하는 일이 다음이다.

## 2026-10-13 저녁 — 전체 테스트가 둘을 더 찾았고, 교시 밖 시각을 없앴다

열한 개를 다 넣은 뒤 머지된 main 에서 전체 스위트 2,204개를 돌렸다. 둘이 떨어졌다. 격리본 이름을 여러 벌로 바꾼 변경과, 고정 이름 `.corrupt` 를 읽던 다른 변경의 테스트가 서로를 몰랐다. 병렬로 고칠 때는 끝에 덧붙이는 목록(테스트 케이스 번호, 제보 코드 표)이 먼저 부딪히고, 그다음이 "내 테스트만 돌린" 틈이다. 지금은 전체가 통과한다.

미뤄 둔 밤 일정도 정했다. 7교시(9:00–16:00) 시간표에 가져온 19:00 수업은 한 일정이 세 자리에 있었다.

| 어디 | 시각 |
|---|---|
| 그리드의 블록 | 15:30 (마지막 반 칸에 그린다) |
| 저장 값과 알람 | 19:00 |
| 편집 시트를 열고 ✓ | 15:30 으로 저장 값이 바뀐다 |

고른 규칙은 **교시형에는 교시 밖 시각이 없다**. 저장 값을 굳히는 함수가 교시 밖 일정도 그리던 자리로 들이고, 옮긴 수를 센다. 파일을 가져올 때는 "교시에 맞춰 조정됨 — 일정 N개" 알럿이 한 번 뜬다.

진 안이 둘이다. 편집 시트만 안 옮기게 막는 안은 작지만 블록은 15:30 에 보이고 알람은 19:00 에 울리는 불일치가 남는다. 교시 밖 일정을 마지막 교시 아래 띠로 따로 그리는 안은 잃는 게 없지만, 교시형 안에 시각형의 정보를 계속 들고 있는 설계라 그리드·내보내기·위젯이 전부 새 칸을 알아야 한다. 교시 일곱 개짜리 축에 19:00 은 없다는 쪽이 모델에 맞았다.

대가는 되돌릴 수 없다는 것이다. 굳힌 뒤 19:00 은 백업 사본과 원본 파일에만 남는다. 그래서 하나를 같이 고쳤다. "교시" 를 눌러만 보고 ✓ 없이 다시 "시간" 을 누르면 일정을 축에 맞추지 않는다. 눌러 보기만 한 시간표의 23:30 수업이 마지막 교시로 옮겨 남으면 안 된다. 굳히는 건 ✓ 하나다.

## 2026-10-13 마지막 점검 — 닫으면 저장하는 시트는, 사용자가 닫지 않아도 닫힌다

같은 세 축을 한 번 더 따라갔다. 이번엔 사례 대신 불변식을 걸었다. 고정 씨앗으로 시간표와 교시 규칙을 무작위로 만들어, 저장하고 읽은 값이 같은지, 유형을 바꿨다 돌아와도 일정 수와 id 가 그대로인지, 교시 규칙을 바꿀 때 사라지는 일정이 알럿이 센 일정과 정확히 같은지를 본다. 저장 왕복 40 파일, 전환 1,500 회, 교시 규칙 400 회. 저장과 셈은 깨지지 않았다. 일부러 셈을 망가뜨린 빌드에서는 162 군데가 떨어졌으니 테스트가 보고는 있다.

구멍은 모델이 아니라 시트에 있었다. 시간표 설정 시트는 취소가 따로 없고 닫으면 저장한다. 표시 범위를 줄여서 일정이 지워질 때만 확인 알럿을 거치는데, 그 방법이 "쓸어내려 닫기를 막는다" 였다. 막힌 건 사용자가 닫는 길뿐이다.

| 시트가 사라지는 길 | 확인 알럿 |
|---|---|
| ✓ | 뜬다 |
| 쓸어내리기 | 막히고, 알럿이 뜬다 |
| 위젯·파일 열기로 다른 시간표가 열린다 | **없다** |
| iPad 에서 창 폭이 바뀌어 화면 구성이 갈린다 | **없다** |

아래 두 길에서는 시트를 띄운 화면이 통째로 다시 만들어지고, 시트 콘텐츠의 `onDisappear` 가 "닫혔으니 저장" 을 그대로 실행한다. 9~18시로 줄여만 두고 다른 시간표의 위젯을 누르면, 원래 시간표의 7시 수업과 22시 수업이 알럿 없이 지워진다. 되돌리기에는 남지만 사용자는 그 시간표를 보고 있지 않다.

고친 건 한 줄이다. 확정 함수가 "확인이 필요한 변경" 이면 `onDisappear` 에서는 저장하지 않는다. 그 상태로 오는 `onDisappear` 는 정의상 사용자가 닫은 게 아니기 때문이다. 되돌리기도 부르지 않는다. 시트 콘텐츠는 잠깐 떨어졌다 다시 붙기도 해서, 아무것도 안 하는 쪽만 두 경우 모두 안전하다.

게이트를 제스처에 걸었던 게 원인이다. 스와이프를 막는 건 화면의 일이고, 저장을 거절하는 건 함수의 일이다. 입구가 하나 더 있으면 제스처에 건 게이트는 없는 것과 같다. 이 길은 코드로 찾았고 실기에서 재현하지는 않았다. 테스트는 확정 함수 수준이고, 실기 확인은 수동 테스트 항목으로 남겼다.

같이 고친 것이 둘 더 있다. 교시 변경을 되돌리면 시간표를 통째로 옛 사본으로 바꾸는데, 그 사본에 목록 순서가 들어 있어서 그 사이 바꾼 순서가 옛 값으로 돌아가 다른 시간표와 겹쳤다. 그리고 단축어로 넣은 일정은 되돌리기에 오르지 않아, 그 전 교시 변경을 되돌리면 같이 사라졌다. 둘 다 "사본으로 되돌리기" 가 사본 안의 되돌릴 대상이 아닌 값까지 되돌린 경우다.

## 2026-10-13 밤 — Android 로 옮기면서 셋은 다르게 정했다

같은 구멍을 Android 판에서도 막았다. 읽지 못한 저장 파일은 따로 보관하고 한 번 알린다. 저장이 실패하면 알럿이 한 번 뜬다. 일부가 깨진 시간표 파일은 통째로 거절한다. 교시 기준 시간표에는 교시 밖 시각이 없다. 여기까지는 iOS 와 같고, 아래 셋은 그대로 옮기지 않았다.

| 자리 | iOS | Android |
|---|---|---|
| 읽기 실패 뒤 복구 | 마지막으로 읽힌 사본(미러)에서 되살린다 | 미러를 두지 않는다. 읽지 못한 원본을 옮겨 두고, 그 사본이 기록이다 |
| "한 번만 알린다" 의 기억 | 앱이 띄울 때 판단한다 | 저장 폴더에 표식 파일을 둔다 |
| 유형 전환 + ✓ 를 되돌리기 한 번으로 | 되돌리기 묶음 | 탭은 되돌리기에 올리지 않고, ✓ 가 전환 전 시간표를 한 번 올린다 |

미러를 뺀 이유는 비용이다. 저장할 때마다 파일을 하나 더 쓰면 그 파일이 깨지는 경우도 하나 더 생긴다. Android 판은 아직 출시 전이라 지켜야 할 설치본이 없다. 읽기 실패가 제보에 보이기 시작하면 다시 본다.

표식 파일은 위젯 때문에 필요했다. Android 위젯은 저장 파일을 직접 읽는다. 깨진 파일을 위젯이 먼저 읽고 옮겨 두면, 다음에 앱을 열었을 때는 파일이 없는 첫 실행과 구분이 안 된다. 메모리에만 적어 두면 앱은 기본 시간표를 조용히 저장하고 알람을 전부 지운다. 그래서 "읽지 못했고, 아직 알리지 않았다" 를 파일로 남긴다.

그 상태에서는 알람도 건드리지 않는다. 화면에는 빈 시간표가 떠 있지만, 사용자가 무언가를 고쳐서 저장에 성공하기 전까지 등록된 알람은 그대로 둔다. 시간표를 고르는 것은 고친 것으로 치지 않는다. 위젯을 누르거나 링크로 열어도 시간표가 골라지는데, 그걸로 첫 저장이 시작되면 사용자는 아무것도 안 했는데 알람이 사라진다. 한계는 하나 있다. 이 상태로 기기를 재시동하면 시스템이 알람을 지우고, 다시 걸 근거가 없다.

되돌리기는 구조가 달라서 묶음을 흉내 내지 않았다. 되돌리기 스택에 묶음 기능을 넣으면 시트가 닫히는 모든 길(✓, X, 뒤로, 쓸어내리기, 알럿, 프로세스 종료)에서 묶음을 닫아야 하고, 하나를 놓치면 그 뒤 편집이 전부 한 묶음이 된다. 대신 유형 탭은 스택에 아무것도 올리지 않고, ✓ 가 규칙 적용·삭제·자리 맞춤을 한 번의 저장으로 하면서 시트를 열 때의 시간표를 한 번 올린다. ✓ 없이 앱을 끄면 다음 실행은 전환 전 시간표로 돌아온다.

옮기는 작업은 그룹별 테스트가 전부 통과한 채로 끝났다. 그런데 전체 1,723개를 한 번에 돌리니 둘이 빨갰다. 하나는 저장 실패가 이제 맥락을 붙여 제보되는데 옛 오류 타입을 기대하던 예전 테스트였다. 다른 하나는 새로 쓴 테스트가 저장 시각이 들어간 파일을 바이트로 비교한 것이었다. 그룹 테스트는 자기 파일만 돌린다. 아무 그룹도 맡지 않은 파일의 테스트는 한 번도 돌지 않았다. 마지막 단계에서 전체를 한 번 돌리도록 절차를 고치는 중이다.

실기에서 본 것은 새로 설치한 앱이 뜨고, 강제 종료 뒤 다시 뜬다는 것까지다. 읽기 실패 알럿, 재실행·재시동 뒤의 알람, 저장 실패 알럿은 테스트와 코드로만 확인했고 수동 테스트 항목으로 남겼다.
