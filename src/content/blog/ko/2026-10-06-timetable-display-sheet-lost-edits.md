교시형 시간표에서 세로축에 점심 칸을 켜 두면, 교시 수를 7에서 5로 줄여도 그리드는 7교시 그대로였다. 점심 표시 스위치는 끄면 곧바로 다시 켜졌다. 고치면서 같은 시트에 숨어 있던 버그를 하나 더 찾았고, 둘 다 "화면은 바뀐 것처럼 보이는데 저장은 안 된" 종류였다.

## 미리보기가 움직이면 "저장된 값이 바뀌었다" 는 신호가 울렸다

표시 방식 시트는 취소가 없는 라이브 시트다. 휠을 돌리면 시트 뒤 그리드가 바로 따라오고, 닫힐 때 한 번 저장한다. 그래서 그리드에는 값이 세 겹으로 있다.

| 겹 | 무엇 |
|---|---|
| 저장본 | 파일에 있는 시간표 |
| 미리보기 상태 | 시트가 돌리는 중인 교시·점심 칸 (`@State`) |
| 화면용 값 | 위 둘로 계산한, 그리드가 실제로 그리는 시간표 |

그리드는 저장된 값이 바뀌면(되돌리기, 가져오기) 미리보기 상태를 저장본으로 다시 읽는다. 문제는 그 신호였다.

```swift
.onChange(of: timetable?.endHour) { _, _ in loadTimetableSettings() }
```

여기서 `timetable` 은 저장본이 아니라 화면용 값이다. 교시형은 교시 하나를 한 칸으로 그리므로 끝 시각이 곧 칸 수인데, 미리보기 축이 저장된 축과 달라지는 순간 다른 갈래로 계산되면서 점심 칸 한 칸이 빠졌다. 7교시에 점심 칸이 있으면 8, 미리보기가 한 번이라도 움직이면 7. 그 8 → 7 이 "저장된 값이 바뀌었다" 로 읽혔다.

찍어 본 로그가 그대로였다.

```
endHour 8 -> 7                  ← 교시 수 휠 7 → 6
reload preview=6 stored=7       ← 미리보기가 저장값으로 되감김
endHour 8 -> 7                  ← 점심 스위치 끔
reload ... storedLunch=1        ← 다시 켜짐
save previewCount=7             ← ✓ 가 저장한 건 옛 값
```

시트 안의 숫자는 5로 남고 그리드만 되감기니, 화면에는 "교시 수 5" 와 7교시 그리드가 같이 있었다. 점심 칸이 꺼진 시간표는 두 갈래의 값이 같아서 멀쩡했다 — 그래서 한참 안 보였다.

고친 건 한 줄 성격이다. 되읽기 신호는 저장본에서만 읽는다. "이 계산값은 편집 중엔 안 변한다" 는 약속으로 버티는 방법도 있었지만, 그 약속은 계산 갈래를 고치는 다음 변경이 깬다. 실제로 이 갈래를 넣은 변경에는 "여기서 끝 시각을 바꾸지 않는다" 는 주석까지 있었다.

## 회귀 테스트는 고치기 전에도 초록이었다

수정하고 UI 테스트를 썼다. 새 시간표를 만들고, 자동으로 뜨는 시트에서 점심 칸을 켜 닫고, 다시 열어 교시 수를 줄인다. 통과했다. 확인 삼아 고치기 전 코드로 돌렸는데, 거기서도 통과했다.

버그를 못 보는 테스트였다. 로그를 보니 전제가 안 서 있었다. 그 첫 시트에서 켠 점심 칸은 저장되지 않았다. 미리보기 상태만 켜진 채였고, 저장본에 점심 칸이 없으니 첫 번째 버그의 조건이 만들어지지 않았다. 그리고 "저장되지 않았다" 는 그 자체가 두 번째 버그였다.

## 시트의 onDisappear 는 닫혔다는 뜻이 아니었다

이 시트는 닫히는 길이 전부 확정이라, 스와이프로 닫힌 경우를 받으려고 콘텐츠의 `onDisappear` 에서도 저장한다. 저장은 깃발 하나로 한 번만 부른다.

새 시간표 직후에는 목록 시트가 아직 닫히는 중에 이 시트가 뜬다. 그때 일어나는 일을 찍어 봤다.

```
35.899  onAppear
35.905  onDisappear        ← 6ms 뒤에 떨어짐, 여기서 "한 번뿐인 저장" 을 씀
36.188  onAppear           ← 0.28초 뒤 다시 붙음. 상태는 그대로
50.538  onDisappear        ← 사용자가 ✓ 로 닫음. 이미 저장했다고 보고 아무것도 안 함
```

SwiftUI 가 콘텐츠를 한 번 뗐다 다시 붙였고, `@State` 는 그 사이 유지됐다. 사용자 앞에 놓인 시트는 처음부터 "이미 확정된" 시트였다. 휠을 돌리면 그리드는 따라오지만 ✓ 는 아무것도 저장하지 않는다. 앱을 다시 켜면 원래 값이다.

처방은 `onDisappear` 가 한 저장을 "닫힘이 아니었을 수 있다" 로 표시해 두고, 콘텐츠가 다시 나타나면 되여는 것이다. ✓ 로 한 저장은 되열지 않는다. 띄우는 시점을 더 늦추는 길도 있었지만 이미 0.6초를 늦추고 있었고, 겹치는 길이는 기기와 모션 설정에 달려 있어 시간으로는 못 막는다.

## 왜 이제야 보였나

이 자리를 정확히 보는 UI 테스트가 이미 있었다. 교시 수를 줄이면 걸친 일정이 남은 교시로 잘리는지 보는 테스트인데, 한동안 빨간 채였다. 이 저장소는 PR 마다 UI 테스트를 돌리지 않아서 아무도 못 봤다.

다른 테스트들은 "닫고 다시 열면 값이 읽힌다" 로 저장을 확인했다. 다시 연 시트는 저장본이 아니라 그리드의 미리보기 상태에서 값을 읽으니, 저장이 안 돼도 통과한다.

## 남긴 규칙

- 저장본을 되읽는 신호는 저장본에서만 읽는다. 화면용으로 가공한 값에 편집 중인 상태가 섞이면, 편집이 곧 되감기 신호가 된다.
- `onDisappear` 에 한 번뿐인 동작을 걸면, 짝이 되는 `onAppear` 에서 되여는 길을 같이 둔다.
- 저장됐는지는 같은 화면을 다시 열어 보지 않는다. 앱을 다시 켠다.
- 새 회귀 테스트는 고치기 전 코드에서 한 번 돌려 빨간 걸 본다. 이번에는 그 한 번이 두 번째 버그를 찾아 줬다.
- 켜고 끄는 설정은 "꺼진 걸 켠다" 만 보지 않는다. 켜서 저장한 뒤 끄기, 켜진 채 옆 설정 바꾸기까지가 한 벌이다.
