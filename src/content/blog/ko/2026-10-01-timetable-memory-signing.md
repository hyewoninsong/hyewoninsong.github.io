SuperTimetable 1.2.0의 테스트 빌드를 준비하면서 기능을 숨기는 옵션을 모두 껐다. 빌드는 업로드에 도달하기 전에 서명에서 멈췄다. 앱이 요청한 Increased Memory Limit 권한을 프로비저닝 프로파일이 허용하지 않는다는 오류였다.

이 권한을 빼면 서명 오류를 피할 수는 있었다. 하지만 테스트하려던 앱의 조건이 달라진다. 요청한 권한을 유지한 채 서명 설정을 맞추기로 했다.

## 앱이 요청한 권한과 프로파일이 허용한 권한은 따로 있었다

앱의 entitlements 파일에는 `com.apple.developer.kernel.increased-memory-limit`가 `true`였다. 파일을 고쳤으니 다음 프로파일에도 들어갈 거라고 생각하기 쉬운데, 프로파일은 개발자 계정에서 허용한 내용을 담는 별도 서명 자료다. 요청이 있다고 허용도 생기는 것은 아니었다.

처음에는 아카이브에서 개발용 프로파일을 잡은 게 문제처럼 보였다. 그런데 새로 생성한 App Store 프로파일을 디코딩해 보니 그쪽에도 메모리 권한이 없었다. 오래된 캐시 하나를 치우거나 프로파일 종류를 바꾸는 것으로 끝낼 문제가 아니었다.

`get-task-allow`와 메모리 권한도 다른 축이었다. 개발용 프로파일에는 디버깅을 허용하는 `get-task-allow=true`가 있었고, 배포용에는 `false`가 있었다. 이 값은 프로파일 종류를 구별하는 데 도움이 됐지만, 어느 쪽에도 빠져 있던 메모리 권한을 설명하지는 못했다.

그래서 프로파일이 언제 만들어졌는지보다 무엇을 허용하는지를 먼저 비교했다. 새로 만들었다는 사실만으로는 검증이 되지 않았다.

## API가 거절한 것은 시도한 등록 경로였다

App Store Connect API로 capability를 등록하려고 했을 때 `INCREASED_MEMORY_LIMIT` 값이 지원되지 않는다는 응답이 돌아왔다. 여기서 Developer Portal에 사람이 로그인해야만 해결된다고 결론 내릴 뻔했다.

하지만 그 응답이 보여 준 것은 해당 API 요청이 거절됐다는 사실이었다. Xcode의 자동 서명 흐름까지 사용할 수 없다는 증거는 아니었다. 다른 도구가 같은 작업을 할 수 있는지는 따로 확인해야 했다.

설치된 `xcodebuild`의 도움말에는 `-allowProvisioningUpdates`를 사용하면 자동 서명 대상의 App ID와 프로파일 등을 생성하거나 갱신한다고 적혀 있었다. 인증 방법에는 Xcode에 추가한 개발자 계정뿐 아니라 App Store Connect API 키도 있었다. 키 파일 경로, 키 ID, issuer ID를 전달하는 세 옵션이었다.

이미 업로드에 쓰는 키가 있었으므로, 로그인 화면으로 넘어가기 전에 이 경로를 시험할 수 있었다. 키가 있다는 사실만으로 성공을 보장하지는 않으니, 실제 생성 결과를 확인하는 작은 기기용 Release 빌드를 먼저 돌렸다.

## 자동 갱신 옵션은 export보다 앞에서도 필요했다

기존 배포 설정에는 `-allowProvisioningUpdates`가 export 단계에만 붙어 있었다. 하지만 실패는 그보다 앞선 archive 서명에서 일어났다. 뒤 단계에서 갱신을 허용해도 앞 단계가 필요한 권한을 얻는 것은 아니었다.

기기용 빌드에 자동 갱신 옵션과 API 키 인증 옵션을 함께 전달했다. 소스의 메모리 권한은 유지했다. 이번에는 프로비저닝 입력 수집을 지나 컴파일로 넘어갔고, Release 빌드도 완료됐다.

더 중요한 결과는 새 개발용 프로파일이었다. 디코딩한 entitlements에 `com.apple.developer.kernel.increased-memory-limit=true`가 생겼다. 이 계정과 앱에서는 Xcode의 API 키 인증을 통한 자동 서명 흐름으로 필요한 권한이 활성화된 것이다.

그 뒤 App Store 프로파일을 다시 생성해 확인했다. 배포용답게 `get-task-allow=false`였고, 메모리 권한은 `true`였다. capability 조회 결과에도 해당 항목이 나타났다. 개발용 빌드 성공과 배포용 프로파일의 허용 값을 각각 확인하면서, 처음의 추측을 실제 결과로 바꿀 수 있었다.

## 새 권한은 업로드 전에 프로파일과 대조한다

이후의 점검은 앱 entitlements와 실제 서명 프로파일의 허용 값을 함께 보는 것으로 정리했다. 권한을 추가한 빌드라면 개발용과 배포용을 따로 확인한다. 프로파일을 재생성했어도 요청한 값이 없으면 성공으로 처리하지 않는다.

공개 API의 오류 메시지도 그 요청의 범위에서 읽기로 했다. 다른 인증이나 관리 경로가 막혔다고 넓혀 해석하기 전에, 도구가 지원하는 옵션과 실제 생성물을 확인한다. 이번에는 그 차이가 대화형 로그인 없이 서명을 해결할 수 있는 길을 남겼다.

여기까지 확인한 결과는 Release 빌드 성공과 메모리 권한이 포함된 배포 프로파일이다. TestFlight 업로드와 Apple의 빌드 처리 완료는 그 다음 단계에서 따로 확인할 일이다.
