SuperTimetable 의 일정 블록은 기본 색 열 개와 파스텔 열 개에서 고른다 (9월 25일부터는 그 뒤에 추천 여섯 세트가 페이지로 이어진다 — 아래 마지막 절). 오늘 아이콘을 iOS 시스템 색으로 다시 그리고 나니 앱 안의 같은 빨강·노랑·파랑이 한 단계 탁하게 보였다. 열 개를 아이콘과 같은 값으로 바꿨고, 파스텔도 한 단계 진하게 다시 뽑았다.

## 탁했던 이유는 채도가 아니라 흰 글자였다

기존 기본 색은 2주 전에 OKLCH 로 골라 놓은 세트였다. 그때 걸었던 규칙이 하나 있다. 열 개 모두 위에 흰 제목이 읽혀야 한다. 앱은 배경의 상대 휘도(WCAG 식)가 0.5 이하면 흰 글자, 넘으면 차콜 글자를 자동으로 고르는데, 열 개 전부를 흰 글자 쪽에 두려고 hue 마다 밝기를 한 단계 깎았다. 노랑이 제일 심했다. 시스템 노랑은 휘도 0.64 인데 우리 노랑은 0.44, 겨자색이었다.

아이콘 블록엔 글자가 없다. 그래서 오늘 아이콘은 그 제약 없이 시스템 색을 그대로 썼고, 나란히 놓자 차이가 그대로 보였다.

![위 줄이 기존 열 개, 아래 줄이 iOS 시스템 색. 노란 블록만 글자가 검게 뒤집힌다.](/blog/timetable-palette-ios-system/before-after.png)

## "노랑만 살짝 어둡게" 는 성립하지 않는다

시스템 색 열 개를 그대로 쓰면 노랑 하나가 자동 모드에서 차콜 글자로 뒤집힌다. 그래서 먼저 떠오른 건 노랑만 조금 깎아서 흰 글자 안으로 넣는 안이었다. 단계별로 깎아 보니 답이 나왔다.

| 노랑 | 휘도 | 자동 글자색 |
|---|---|---|
| 시스템 노랑 `#FFCC00` | 0.64 | 검정 |
| 6% 어둡게 | 0.56 | 검정 |
| 10% 어둡게 | 0.51 | 검정 |
| 13% 어둡게 `#DEB100` | 0.47 | 흰색 |
| 기존 노랑 `#D7AB09` | 0.44 | 흰색 |

흰 글자로 넘어가는 경계가 13% 지점이고, 거기서 이미 기존 겨자색과 구분이 안 간다. 노랑은 원래 밝은 색이라 흰 글자가 읽힐 만큼 어두워지면 더는 노랑이 아니다. "살짝" 이 없다.

![시스템 노랑을 단계별로 어둡게 한 블록들. 흰 글자로 넘어가는 순간 기존 겨자색과 같아진다.](/blog/timetable-palette-ios-system/yellow-steps.png)

남은 선택지는 둘이었다. 노랑은 시스템 값 그대로 두고 글자만 검게 가든가, 흰 글자 통일이 우선이면 노랑만 기존 값을 남기고 아홉 개만 바꾸든가. 전자를 골랐다. 파스텔 열 개가 이미 전부 차콜 글자라 앱 안에서 낯선 문법이 아니고, 시간표마다 글자색을 밝게·어둡게 고정하는 설정도 있다. 아이콘과 앱 색이 정확히 같은 쪽이 "쨍하게" 의 목적에 가깝다.

## 파스텔은 밝기를 조금 내려 채도 자리를 만들었다

파스텔 열 개는 시스템 색의 OKLCH hue 를 그대로 따라가며 L 0.85, C 0.12 로 뽑았다. 기존은 L 0.87 에 C 0.07~0.10 이었다. 밝기를 0.02 내린 건 채도 여유 때문이다. sRGB 색역은 밝은 쪽에서 좁아져서, 같은 밝기에서 빨강과 파랑은 C 0.08 근처에서 벽에 닿는다. C 0.14 로 균일하게 밀어 보면 민트와 초록만 튀고 빨강·파랑은 그대로다. 그래서 "hue 마다 색역 안 최대, 상한 0.12" 로 두고 노랑만 L 0.88 로 올렸다. 노랑은 어두워지면 올리브가 된다. 회색은 아이콘의 눈금 점과 같은 값이라 그대로 뒀다.

![최종 스무 색. 진한 열 개는 노랑만 검은 글자, 파스텔 열 개는 전부 검은 글자.](/blog/timetable-palette-ios-system/final-twenty.png)

## 값이 같아도 아이콘과 앱을 묶지는 않았다

2주 전엔 "아이콘 색 = 앱 기본 색" 으로 묶었다가 오늘 아침 풀었다. 흰 글자 제약이 아이콘까지 상속돼 아이콘이 탁해 보였기 때문이다. 오늘 오후 앱 색을 아이콘과 같게 바꿨지만 다시 묶지는 않았다. 제약이 다른 두 곳은 언젠가 다시 갈라진다. 아이콘 값은 아이콘 렌더 스크립트가, 앱 값은 팔레트 모델이 따로 갖는다.

계약 테스트는 "진한 열 개 전부 흰 글자" 에서 "노랑만 차콜, 나머지 흰" 으로 바꿨다. 다음에 색을 갈 때 휘도 0.5 를 넘는 색이 늘면 그 예외 목록이 먼저 깨진다.

## 2026-09-25 — 파스텔이 마음에 안 들어서, 빼는 대신 여섯 세트를 더 붙였다

이틀 써 보니 파스텔 열 개가 손에 안 붙었다. 처음 생각은 파스텔을 다시 뽑는 것이었는데, 그 열 개는 이미 저장된 일정과 스토어 스크린샷이 hex 로 물고 있다. 바꾸면 기존 일정 색은 그대로라도 "내가 고른 색이 팔레트에 없다" 가 된다. 그래서 스무 색은 한 칸도 건드리지 않고, 기본 탭에 페이지를 넣어 그 뒤에 추천 색을 열 개씩 여섯 세트 붙였다. 기본 탭은 한 페이지 스무 칸에서 네 페이지 여든 칸이 됐고, 아래 점 네 개가 생겼다.

![여섯 세트를 라이트·다크 지면에 나란히. 열은 늘 같은 hue, 세트마다 밝기와 채도만 다르다.](/blog/timetable-palette-ios-system/six-sets.png)

여섯 세트는 hue 로 가르지 않았다. 열 개 모두 위 진한 색의 OKLCH hue 를 그대로 쓰고(빨강·주황·노랑·초록·민트·하늘·파랑·보라·분홍·회색 순), 세트마다 밝기 L 과 채도 C 만 다르다. vivid (L 0.74 / C 0.19), candy (0.80 / 0.16), deep (0.52 / 0.15), dusty (0.68 / 0.065), mist (0.92 / 0.045), night (0.40 / 0.085). 어느 페이지를 넘겨도 같은 열이 같은 색 계열이라, "빨강 계열이 필요한데 덜 쨍한 것" 은 첫 열에서 페이지만 넘기면 된다. 노랑과 주황은 밝기를 내리면 올리브와 갈색이 되므로 세트마다 그 둘만 L 을 0.03~0.14 올렸고, 색역 밖으로 나가는 색은 채도만 깎았다.

![deep 과 dusty 가 든 세 번째 페이지. 진한 빨강을 고르자 링이 뜨고 뒤의 편집 시트 헤더가 같은 색이 됐다.](/blog/timetable-palette-ios-system/page-deep-dusty.png)

### 한 페이지에 두 세트, 세트 이름은 없다

페이지 한 장은 5열 4줄 스무 칸으로 못박혀 있다. 커스텀 탭이 그 형태를 쓰고, 팝오버 높이가 거기서 나온다. 세트 하나가 열 개 = 두 줄이라, 세트마다 한 페이지를 주면 아래 두 줄이 늘 빈다. 그래서 한 페이지에 두 세트 — 위 두 줄이 한 세트, 아래 두 줄이 다른 세트다. 기존 페이지도 이미 "진한 열 개 위, 파스텔 열 개 아래" 라 같은 문법이다.

세트 이름을 캡션으로 넣는 안은 버렸다. 캡션 한 줄이 들어갈 자리가 없고(높이가 못박혀 있다), 지금 첫 페이지도 진한/파스텔 줄에 이름이 없다. 이름은 애널리틱스에만 남는다 — 어느 세트가 실제로 쓰이는지 세는 용도다.

점 행은 지금 보고 있는 탭의 페이지만 센다. 기본에서 네 개, 커스텀에서 커스텀 페이지 수. 기본 4 + 커스텀 n 을 한 줄로 이으면 세그먼트가 이미 말하는 걸 반복하고, 커스텀이 열 페이지면 점이 열네 개가 된다.

### 첫 안의 한 세트가 파스텔과 정확히 같은 색을 냈다

처음 뽑은 여섯 세트 중 하나는 "bright" 였다. L 0.82 / C 0.13. 파스텔(L 0.85 / C 0.12)보다 살짝 진한 자리를 노렸는데, 주황이 `#FFBF85` — 파스텔 주황과 hex 까지 똑같이 나왔다. 두 색 모두 그 밝기에서 주황이 sRGB 색역에 먼저 걸려 채도가 같은 값으로 깎이기 때문이다. 같은 hex 가 두 칸이면 선택 링이 두 곳에 뜨고, "지금 색이 든 페이지" 판정도 둘 중 하나를 고른다.

교훈은 단순하다. 파스텔과 같은 밝기 대역에 세트를 하나 더 두면 색역 벽 때문에 결국 같은 색이 나온다. bright 는 버리고 한 단계 진한 candy (L 0.80 / C 0.16) 로 갔고, 팔레트 생성 스크립트와 계약 테스트 양쪽에 "여든 색 hex 전부 서로 다를 것" 을 넣었다. 다음에 세트를 더 붙이면 겹치는 순간 스크립트가 먼저 멈춘다.

캡처 프로브에서도 하나 배웠다. 페이지마다 첫 스와치 x 가 같은지 재려고 첫 페이지의 첫 스와치 프레임을 기준으로 잡았는데, 그 스와치가 선택 링을 두르고 있어서 프레임이 링만큼(약 5pt) 컸다. 세 페이지가 전부 "5pt 어긋남" 으로 떨어졌지만 실제로는 정렬돼 있었다. 선택 상태의 요소는 기준 프레임으로 쓰면 안 된다.

## 이력

- 2026-09-23 — 기본 열 개를 iOS 시스템 색으로, 파스텔 재선정, 노랑만 차콜 글자.
- 2026-09-25 — 스무 색은 두고 기본 탭에 페이징, 추천 열 색 × 여섯 세트(같은 hue, L/C 만 다름). bright 세트가 파스텔과 hex 충돌 → candy.
