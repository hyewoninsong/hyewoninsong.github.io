하루 플래너에서 할일은 한 번 만들면 지울 수 없었다. 더 안 할 것은 **보관**으로 치우고, 기록은 남는다. 이번에 그 규칙을 뒤집어 진행 중이든 보관됨이든 **영구 삭제**를 열었다. 대신 지우기 전에 무엇이 함께 사라지는지 숫자로 보여 준다.

## 보관함이 두 가지를 담고 있었다

이 앱에서 할일의 이름과 색을 바꾸면 과거 배치까지 전부 따라간다. 할일을 지운다는 건 그 할일로 쌓은 기록 — 배치, 잔디, 통계 — 이 통째로 사라진다는 뜻이다. 그래서 처음부터 삭제를 만들지 않았다.

그런데 보관으로 해결되지 않는 것이 남았다. 오타로 만든 할일, 테스트로 만든 할일, 프로필을 잘못 고른 할일. 기록할 게 하나도 없는데 보관함에 영원히 쌓인다. 보관함이 "나중에 다시 할 것"과 "쓰레기"를 같이 담기 시작하면 보관 자체가 안 쓰인다.

## 두 자리, 경고 한 번

삭제하는 길은 둘이다. 행을 왼쪽으로 밀면 나오는 빨간 `삭제`, 그리고 편집 모드에서 여러 개를 고른 뒤 누르는 휴지통.

![행을 밀면 삭제와 보관이 나온다. 풀스와이프로 튀어나오는 첫 동작은 계속 보관이다](/blog/planner-delete-todos/swipe-actions.png)

풀스와이프 자리는 일부러 보관에 남겼다. 손이 미끄러져 끝까지 밀었을 때 실행되는 동작은 되돌릴 수 있는 쪽이어야 한다.

경고 창은 이름과 **함께 사라질 배치 개수**를 말한다. "배치 12개와 지금까지의 기록이 함께 사라집니다. 되돌릴 수 없어요 — 잠시 치워 두려면 보관하세요." 삭제 비용을 문장이 아니라 숫자로 보여 주는 게 핵심이다. 12개짜리와 0개짜리는 같은 결정이 아니다.

![삭제 경고 창. 대상 이름과 함께 사라질 배치 개수를 먼저 말한다](/blog/planner-delete-todos/delete-alert.png)

## 되돌리기 스택에는 넣지 않았다

이 앱에는 쓰기 전체를 덮는 되돌리기 스택이 있다. 삭제도 거기 넣는 게 자연스러워 보이지만 넣지 않았다. 창에서 "되돌릴 수 없어요"라고 말해 놓고 되돌리기 버튼이 되살리면 둘 중 하나는 거짓말이다. 배치 수백 개의 역연산을 항목 하나에 담아 스택(최대 50)을 밀어내는 것도 비용이다.

대신 확인 없이 지우고 되돌리기로 복구하는 선택지도 있었다. 이 앱은 실제로 **배치** 삭제를 그렇게 한다 — 확인 창 없이 지우고, 되돌리기가 받는다. 할일은 자릿수가 다르다. 배치 하나는 5분이고 할일 하나는 반년 치 기록이다.

30일 뒤 비워지는 휴지통도 검토했다. 상태가 셋(진행 중·보관·휴지통)으로 늘고 만료 스케줄이 붙는다. 경고 한 번이면 되는 일에 그만한 구조를 들일 이유가 없었다.

## 지운 객체를 경고 창이 다시 읽는다

처음 구현은 경고 창이 대상 `Todo` 를 그대로 들고 있었다. 삭제를 누르면 지우고, 창이 닫힌다. 그런데 닫히는 프레임에서 SwiftUI 는 제목과 본문을 한 번 더 평가한다 — 그 안에 `todo.title` 이 있다. 이미 컨텍스트에서 지워진 `@Model` 객체를 읽는 것이다.

처방은 단순하다. 창이 모델이 아니라 **값**을 들게 했다.

```swift
private struct DeleteRequest: Identifiable {
    let id = UUID()
    let ids: [UUID]      // 확인 뒤 다시 찾아 지운다
    let title: String
    let message: String
}
```

묻는 순간 이름과 개수를 문자열로 굳혀 두면, 지운 뒤에 창이 몇 번 더 그려져도 읽을 게 남아 있다. 같은 이유로 확인 콜백은 모델 배열이 아니라 id 목록으로 대상을 다시 찾는다.

되돌리기 스택은 비우지 않았다. 항목이 모델 참조가 아니라 **id 스냅샷**으로만 이뤄져 있으니, 지워진 할일을 가리키는 옛 항목은 조회가 nil 을 돌려주고 그냥 넘어갈 거라고 봤다. 여기까지는 맞았는데 "그냥 넘어간다"를 안전하다고 읽은 게 틀렸다 — 아래 2026-09-21 절.

## 2026-09-21 — 조용히 넘어가는 되돌리기는 고장 난 되돌리기였다

위에서 "지워진 할일을 가리키는 옛 항목은 조회가 nil 이라 아무 일도 하지 않는다"고 썼다. 사실이지만, 그게 왜 괜찮은지는 한 번도 따져 보지 않았다. 따져 보니 괜찮지 않았다.

역연산은 전부 이 모양이다.

```swift
ctx.block(id: id)?.parkedAt = nil     // 배치가 없으면 옵셔널 체이닝이 통과
```

할일을 영구 삭제하면 그 할일의 배치가 cascade 로 전부 사라진다. 그 순간 스택에 남아 있던 그 할일 관련 항목 — 옮기기, 완료, 서랍에 넣기, 배치 삭제 — 이 한꺼번에 **가리킬 것이 없는 항목**이 된다. 그래도 버튼은 켜져 있다(스택이 비지 않았으니까). 누르면 스택이 한 칸 줄고, 화면은 그대로다. 죽은 항목이 다섯이면 다섯 번 눌러야 살아 있는 칸에 닿는다. 사용자가 읽는 건 하나뿐이다 — 되돌리기가 고장 났다.

더 나쁜 것도 있었다. 그 죽은 항목은 다시 실행 스택으로 넘어간다. 그중 `할일 추가` 항목의 다시 실행은 스냅샷 복원이라, **영구 삭제한 할일을 되살린다.** 경고 창에서 "되돌릴 수 없어요"라고 말해 놓고 오른쪽 화살표 한 번이면 돌아오는 셈이다.

고친 방향은 옵셔널 체이닝을 걷어내는 것이다. 역연산이 **고쳤는지를 `Bool` 로 돌려준다.**

```swift
extension ModelContext {
    func apply(block id: UUID, _ body: (TodoBlock) -> Void) -> Bool {
        guard let block = block(id: id) else { return false }
        body(block)
        block.updatedAt = .now
        return true
    }
}
```

스택은 적용된 항목을 만날 때까지 계속 팝하고, 못 고친 항목은 **버린다** — 반대쪽 스택에도 넣지 않는다. 켜져 있는 되돌리기 버튼은 이제 항상 뭔가를 되돌린다. 영구 삭제가 남긴 죽은 항목은 사용자 눈에 띄지 않게 스스로 정리되고, 지운 할일은 다시 실행으로도 돌아오지 않는다.

묶음 동작(여러 배치를 한꺼번에 미는 것)에서 한 번 더 걸렸다. "한 칸이라도 먹으면 적용"을 `entries.reduce(false) { $0 || $1.undo(ctx) }` 로 접었는데, `||` 는 단락 평가다 — 첫 칸이 성공하면 나머지 칸의 역연산이 **아예 실행되지 않는다**. 접지 말고 전부 돌려야 한다.

이 조사는 "서랍에 넣고 빼는 게 되돌리기가 안 된다"는 보고에서 시작했다. 정작 서랍 경로 자체는 멀쩡했다 — 넣기·꺼내기 × 되돌리기·다시 실행 × 오늘/다른 날을 UI 테스트로 여섯 가지 돌려 전부 통과했다. 같은 증상을 만드는 자리는 다른 데 있었다. 증상을 그대로 믿고 그 코드만 보다가는 못 찾을 뻔했다.

한 가지는 서랍 쪽에도 남았다. 되돌리기가 배치를 서랍으로 돌려보낼 때 아무 신호가 없었다 — 화면에서 블록이 사라지는 게 전부다. 넣을 때 쓰던 "서랍에 넣었어요" 연출을 되돌리기에도 붙였다. 어디로 갔는지 말하지 않으면 그것도 "안 먹었다"로 읽힌다.

## 남은 것

프로필 삭제는 여전히 없다. 프로필을 지우는 건 그 안의 할일 전부를 지우는 일이라, 필요해지면 따로 결정할 문제다. 실수로 지웠다는 이야기가 나오면 그때 "지우기 전 내보내기"를 먼저 본다 — 휴지통보다 싸다.
