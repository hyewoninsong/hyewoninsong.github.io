시간표 앱은 일정을 만들 때, 색을 고를 때, 시간표를 공유할 때마다 이벤트를 보낸다. 그런데 그걸 보고서에서 요일별로, 공유 방식별로 쪼개 보려면 매개변수를 따로 **등록**해야 한다. 등록 후보를 추리려고 코드를 열었다가, 등록해봐야 빈칸이거나 갈라진 표가 나올 값들만 잔뜩 보냈다는 걸 알았다.

## 등록이 소급되지 않는다는 게 전부였다

매개변수는 등록한 **시점 이후** 수집분부터만 보고서에 뜬다. 이미 쌓인 데이터는 어휘가 잘못돼 있어도 되돌릴 방법이 없다. 그러니 순서가 하나뿐이다 — 값을 먼저 고치고, 그다음에 등록한다. 그래서 이번 작업은 "무엇을 등록할까" 가 아니라 "무엇이 등록 가능한 형태인가" 가 됐다.

## 값을 막는 세 가지

**하나, `Bool` 은 문자열이 아니다.** 스위프트 `Bool` 을 `[String: Any]` 에 넣어 SDK 로 넘기면 경계를 넘으면서 `NSNumber` 로 바뀐다. 파이어베이스는 그걸 **숫자** 매개변수로 기록한다. 텍스트 측정기준 후보에 아예 안 올라오고, 숫자 측정항목으로 등록하면 "잠금 여부의 평균" 같은 게 나온다. 그래서 낱말로 보내기로 했다.

```swift
private func flag(_ value: Bool) -> String { value ? "true" : "false" }
return ["is_locked": flag(isLocked)]
```

**둘, 현지화 문자열은 값을 쪼갠다.** 요일을 보낼 때 화면에 쓰는 이름을 그대로 재사용하고 있었다. 이 앱은 다섯 개 언어라 같은 월요일이 `월`·`Mon`·`月` 로 들어간다. 더 나쁜 건, 번역을 한 번 고치면 그 시점부터 또 갈라지고 과거 데이터는 옛 문구로 남는다는 것이다. 표시용과 **별개인** 고정 키를 뒀다.

```swift
var analyticsKey: String {   // mon, tue, … — 절대 현지화하지 않는다
    switch self { case .monday: return "mon"; /* … */ }
}
```

같은 이유로 설정은 `rawValue` 로, 색은 팔레트 슬롯 이름(`basic_0`…`pastel_9`)으로 보낸다. 사용자가 직접 만든 색의 hex 는 보내지 않는다 — 값 종류가 무한해서 측정기준이 안 되기도 하고, 애초에 사용자가 만든 값을 밖으로 내보내지 않는 게 이 앱의 규칙이다.

**셋, 아무도 안 덮어쓰는 기본값.** 일정 편집 이벤트에 "무슨 편집인지" 를 담는 매개변수가 있었는데, 함수 기본값이 `"general"` 이고 이를 덮어쓰는 호출부가 하나도 없었다. 등록하면 열이 하나뿐인 표가 나온다.

고치는 방향이 갈렸다. 호출부마다 값을 손으로 넣을 수도 있었지만, 편집 시트는 제목·색·시각·알람·메모를 **한 번에** 저장해서 호출부가 분류를 모르는 게 정당한 경우였다. 그래서 값을 받지 말고 유도하기로 했다 — 이전 값과 견줘 바뀐 필드를 한 낱말로 요약한다. 바뀐 게 하나면 그 이름, 여럿이면 `multi`.

이쪽을 고른 이유는 앞으로다. 새 저장 경로가 생겨도 자동으로 분류된다. 기본값 방식이 조용히 굳었던 것과 정확히 반대다. 제스처가 곧 의미인 경로(드래그·리사이즈)만 값을 명시하고, 되돌리기로 돌아간 편집은 `undo` 로 따로 찍어 사람이 낸 편집과 섞이지 않게 했다.

## 정의해 둔 이벤트와 찍히는 이벤트는 다르다

여기까지 고치고 호출부를 세어 봤더니, 로깅 래퍼 스무 개 중 **열다섯 개가 아무 데서도 불리지 않고** 있었다. 이벤트 열거형에 이름이 있으니 찍히는 줄 알았던 것이다.

더 나온 것도 있다. 그중 몇은 **기능이 이미 사라진 뒤**였다. 시간표를 겹쳐 보는 오버레이 모드는 저장 파일 v5 에서 지워졌고, 색 즐겨찾기는 저장소만 남고 화면이 없고, 프리미엄 색이라는 개념은 이 앱에 존재한 적이 없다. 위젯 설정 이벤트는 원리상 못 찍는다 — 위젯 타깃에는 파이어베이스가 없어서, 앱이 볼 수 있는 건 위젯을 눌러 앱이 열릴 때의 딥링크뿐이다.

그래서 찍을 자리가 있는 것은 실제 지점에 연결하고(시간표 열기, 편집 모드 진입, 이동, 복제, 색 선택, 설정 변경 등 열다섯 군데), 찍을 자리가 없는 것은 **지웠다**. 남겨 두면 다음에 보는 사람이 또 "수집되는 이벤트" 로 읽는다. 이번 조사가 시작된 이유가 바로 그 오해였다.

## 왜 못 잡았나

파이어베이스는 이 셋을 하나도 거절하지 않는다. 타입이 틀렸다는 경고도, 값 종류가 폭발한다는 경고도 없다. 게다가 디버그 뷰와 실시간 보고서는 등록 없이도 원시 매개변수를 그대로 보여준다 — 잘 들어가는 것처럼 보인다. 측정기준 등록은 그다음 단계고, 거기서야 드러난다.

코드 쪽에서 잡히게 계약 테스트를 넣었다. 샘플 이벤트의 매개변수 중 `Bool` 이 하나라도 있으면 실패하고, `is_`·`has_` 로 시작하는 값이 `"true"`/`"false"` 인지, 요일 키가 고정 ASCII 인지 단언한다. 함정은 이 테스트에도 있다 — 샘플 배열에 빠진 이벤트는 검사되지 않는다. 그래서 "이벤트를 추가하면 샘플에도 한 줄 넣는다" 를 규칙으로 적어 뒀다.

## 지금 상태

어휘는 정리됐고, 이제 콘솔에서 등록할 차례다. 측정기준으로는 공유 방식·오류 유형·오류 맥락·편집 종류·이동 방식·설정 키·색 이름·요일을, 측정항목으로는 일정 길이·시간표 수·전체 일정 수·체류 시간을 올린다. 등록한 날부터의 데이터만 보이니, 며칠 뒤에야 이 작업이 맞았는지 알 수 있다.
