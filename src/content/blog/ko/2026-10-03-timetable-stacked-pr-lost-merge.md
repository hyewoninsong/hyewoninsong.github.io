교시형 시간표에서 세로축에 점심 칸을 보일지 고르는 스위치가 화면에 없다는 보고가 왔다. 그 스위치는 이미 두 번 만들었고, 두 PR 모두 GitHub 에서 `MERGED` 상태였다.

## MERGED 는 "main 에 있다" 가 아니다

코드를 찾아보니 main 에는 점심 칸 관련 줄이 하나도 없었다. 두 PR 은 모두 **다른 PR 위에 쌓여** 있었다. 기능 B 를 기능 A 의 브랜치 위에서 만들고, PR 의 베이스도 `feat/a` 로 둔 형태다.

순서는 이랬다.

1. A 가 main 으로 squash 머지된다. main 에는 A 의 커밋 하나만 새로 들어가고, `feat/a` 브랜치는 그대로 남는다.
2. 몇 초 뒤 B 를 머지한다. B 의 베이스는 여전히 `feat/a` 라서, B 는 **`feat/a` 로** 들어간다.
3. GitHub 은 B 를 `MERGED` 로 표시한다. main 과는 아무 상관이 없다.

두 번째 유실은 첫 번째를 되살리는 PR 에서 났다. 아래 PR 이 머지되고 위 PR 이 머지되기까지 14초였다. 연달아 버튼을 누르는 동안 베이스 칸을 다시 볼 틈이 없었다.

## 같은 식으로 빠진 게 여덟 개 더 있었다

`main` 이 아닌 베이스로 머지된 PR 을 전부 뽑아 보니 열 개였다. 점심 칸 둘을 빼고도 여덟 개가 main 에 없었다. 빈 시간 맞추기 쪽 넷(결과가 없을 때 조건을 넓히자는 제안, 빈 칸 안 시간 제안, 공유 이미지의 참여자 표시, 웹 링크로 시간표 요청)과, 교시 쪽 넷(다른 시간표의 교시 가져오기, 1분 단위 교시 길이, 넘칠 때의 복구 동작, 저장 전 일정 변화 목록)이다.

머지 커밋이 main 의 조상인지는 `git merge-base --is-ancestor` 로 바로 알 수 있다. 하지만 squash 머지는 원래 커밋을 main 에 남기지 않으므로 "조상이 아님" 만으로는 판정이 안 된다. 그래서 각 PR 이 새로 만든 타입과 함수 이름을 main 에서 하나씩 찾았다. 여덟 개 모두 0건이었다.

점심 칸 스위치는 다시 main 위로 옮겼다. 그 사이 main 에 화면 배율 작업이 두 개 들어와 있어서, 점심 칸 라벨과 회색 칸에도 같은 배율을 곱해야 했다. 나머지 여덟 개는 복구하지 않기로 했다. 빈 시간 화면과 교시 설정 화면이 그 뒤 크게 바뀌어서 그대로 옮길 수 없고, 다시 만든다면 지금 화면에 맞춰 새로 설계하는 편이 낫다.

## 문서 경고로는 막지 못했다

첫 번째 유실 뒤에 "베이스는 main 으로" 라는 가이드를 적어 두었다. 두 번째 유실은 그 가이드를 읽고 쓴 복구 PR 에서 났다. 그래서 이번에는 설정을 바꿨다.

- 저장소의 **Automatically delete head branches** 를 켰다. A 가 머지되면서 `feat/a` 가 지워지면, GitHub 이 그 위에 쌓인 B 의 베이스를 main 으로 자동으로 바꾼다. 꺼져 있었기 때문에 이 재지정이 일어나지 않았던 것이다.
- PR 을 만드는 절차에는 "main 이 아닌 베이스로 쌓으려면 이 설정이 켜져 있는지 먼저 확인한다" 는 단계를 넣었다.
- 고친 기능이 다시 없다고 보고되면, 열린 PR 과 함께 **main 이 아닌 베이스로 머지된 PR** 도 조회한다.

## 남은 것

화면에 `MERGED` 가 보여도 베이스가 main 이 아니면 그 기능은 앱에 없다. 기록이 "구현됨" 이라고 해도, 다시 쓰기 전에 main 에서 이름을 한 번 찾아본다.
